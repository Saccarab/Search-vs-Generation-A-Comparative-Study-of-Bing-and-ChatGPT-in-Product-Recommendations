\chapter{Findings \& Analysis}
\label{ch:findings}

\begin{itemize}
    \item \textbf{The ``Fan-Out Strategy'' (Implicit vs.\ Explicit Retrieval):}
    \begin{itemize}
        \item \textbf{Gemini's Freshness Obsession:} 96.7\% of Gemini runs (297/307) explicitly inject a year (2025 or 2026) into their fan-out queries, with 74.3\% (228/307) placing this signal in the very first query (Index 0). This drives Gemini's aggressive ``Listicle Uptake.''
        \item \textbf{GPT's Multi-Turn Expansion:} While GPT only uses explicit years in 5.1\% of runs, it exhibits a ``Multi-Turn Fan-Out'' phenomenon where it issues secondary and tertiary queries (3+ queries) in response to initial results, effectively ``hunting'' for specific citations before finalizing the response.
        \item \textbf{Implicit Localization Bias:} Implicit localization signals (non-English fan-out queries from English prompts) were observed in 13.1\% of GPT runs and 4.6\% of Gemini runs, demonstrating how retrieval environment (IP/locale) can steer grounding even without user intent.
    \end{itemize}
    \item \textbf{The ``Provider Pivot'' (Enterprise vs.\ Personal):} GPT Personal shows significantly higher overlap with Google (\textasciitilde65\%) than GPT Enterprise (\textasciitilde28\%), suggesting a deployment-specific retrieval strategy where Personal runs are likely multi-provider (Bing + Google) while Enterprise is restricted to the Bing/Azure ecosystem.
    \item \textbf{The ``UI Erasure'' \& Invisible Citations:} By expanding retrieval depth to Rank 200, we discovered that a significant portion of LLM citations are ``invisible'' to human searchers (Rank 11--30+). This proves LLMs act as ``Deep Hunters,'' extracting high-quality content that search engine UIs have effectively buried.
    \item \textbf{The ``Page 2 Cliff'' \& Position Bias:} Despite the ability to ``Deep Hunt,'' citation density exhibits a violent drop-off after Rank 10 (the ``Page 2 Cliff''). This confirms that position bias remains the dominant factor in GenAI grounding, creating a ``Winner-Take-All'' dynamic for the first elastic page.
    \item \textbf{The ``Structural Filter'' (Selection Drift):} Models exhibit statistically significant preferences for specific Content DNA. Gemini, for instance, shows a +8.7pp ``hunt'' for numbered lists, while GPT Personal shows a +12.2pp preference for tables in listicles.
    \item \textbf{Listicle Uptake \& Host Bias:} LLMs exhibit a ``graduation'' effect, preferentially citing the primary product pages recommended within retrieved listicles, but this is tempered by a measurable ``Host Exclusion'' bias where certain domains are systematically ignored despite being present in the ``Menu.''
\end{itemize}

\section{Retrieval Strategy \& Fan-Out Analysis}
\label{sec:fanout}

\textit{Before analyzing citation overlap, we examine the retrieval phase: how the models reshape the user prompt into multiple search queries. Methodology and instrumentation are defined in Sections~2.3.4, 2.7.1, and 2.7.2.}

\subsubsection{The Three-Layer Architecture (as observed)}
\label{sec:three-layer}

Our network instrumentation reveals a three-layer pipeline, not a monolithic model:

\begin{lstlisting}
Layer 1: SONIC CLASSIFIER (fires once, <15 ms)
  |  Decides: search vs. no-search
  |  Outputs: simple_search_prob, complex_search_prob, no_search_prob
  |  Deterministic for same input (byte-identical across runs of same prompt)

Layer 2: SONICBERRY ORCHESTRATOR (alpha.sonic_thinky_v1_paid)
  |  Manages the web.run tool-call loop
  |  Each web.run call dispatches exactly 2 queries (fixed pair-generation)
  |  Tracks search_turns_count (1, 2, 3...)

Layer 3: GENERATION MODEL (gpt-5-2)
  |  After each web.run, evaluates retrieved results in context
  |  Decides whether to call web.run again (agentic re-search)
  |  Non-deterministic: same input can produce 1-3 search turns
  |  Selects sources -> generates response with inline citation tokens
\end{lstlisting}

The high-level flow as observed in the event stream:
\begin{enumerate}
    \item \textbf{User prompt received}
    \item \textbf{Search decision (Layer 1)}: the Sonic Classifier outputs a 3-class probability distribution and evaluates it against thresholds in priority order (\texttt{no\_search} $\rightarrow$ \texttt{complex} $\rightarrow$ \texttt{simple}). If \texttt{no\_search\_prob} $\geq 0.175$, search is suppressed; otherwise search fires.
    \item \textbf{Fan-out query generation + retrieval (Layer 2--3)}: the model calls the \texttt{web.run} tool, which dispatches exactly 2 reformulated queries. Results return as \texttt{search\_result\_groups}.
    \item \textbf{Re-search decision (Layer 3)}: the generation model evaluates the retrieved pool and may call \texttt{web.run} again (incrementing \texttt{search\_turns\_count}). This creates the agentic re-search loop --- 94\% of runs complete in 1 turn (2 queries), 2.5\% require 2 turns (4 queries), 0.2\% require 3 turns (6 queries).
    \item \textbf{Selection}: the model promotes some sources to be cited inline, and may also attach extra sources as ``additional.''
    \item \textbf{Generation}: answer text is streamed + citation tokens are inserted (e.g., \texttt{citeturn0search0}) and merged into the final response (``multi-chip'').
\end{enumerate}

\subsection{ChatGPT Search Trigger Behavior}
\label{sec:search-trigger}

\textit{When does ChatGPT decide to search at all?}

\begin{itemize}
    \item \textbf{Overall search rate:} \textbf{89.0\%} of 474 runs triggered web search (422/474). Enterprise: \textbf{91.1\%}, Personal: \textbf{86.9\%} --- a 4.2~pp gap.
    \item \textbf{Classifier behavior:} The Sonic Classifier output a median \texttt{simple\_search\_prob} of \textbf{96.8\%} for product-recommendation prompts. Neither the \texttt{complex\_search\_threshold} (0.4) nor the \texttt{no\_search\_threshold} (0.175) was ever crossed --- all runs fell into ``simple search'' territory. The closest miss: P016 enterprise at \texttt{no\_search\_prob} = 0.1737 (missed the 17.5\% gate by 0.0013).
    \item \textbf{External suppression:} The 52 no-search runs were \textbf{not} caused by the classifier's probability output:
    \begin{itemize}
        \item 39 runs had \textbf{null classification} (classifier never executed; raw network response files were empty)
        \item 13 runs had the classifier \textbf{overridden} despite \texttt{simple\_search\_prob} as high as 99.7\% --- pointing to server-side A/B gates, tool routing (\texttt{passthrough\_tool\_calls}), or session-level factors, predominantly on Personal accounts (11 of 13 overrides)
    \end{itemize}
    \item \textbf{Prompt-level consistency:} 61/79 prompts (77.2\%) always triggered search across all 6 runs; 6 prompts (7.6\%) never triggered search; 12 prompts (15.2\%) showed mixed behavior --- P016 had a perfect 50/50 split.
    \item \textbf{Citation impact:} Search-triggered runs averaged \textbf{9.94 citations/run} vs \textbf{2.62} for no-search runs (\textasciitilde4x). Enterprise no-search runs averaged just 1.10 citations; Personal no-search runs managed 3.65, suggesting Personal more readily generates citation-like references from parametric memory.
    \item \textbf{Ghost citations:} 7 runs (all Personal) produced citation-formatted markers with \textbf{zero backing URLs} --- hallucinated citation syntax. A further 5 runs produced \textbf{fully sourced citations without search} (up to 14 citations from parametric URL recall alone).
\end{itemize}

\paragraph{Sonic Classifier configuration (observed across all 474 runs):}
\begin{itemize}
    \item \textbf{Classifier:} \texttt{sonic\_classifier\_5p2\_3cls\_ev3} (model: \texttt{snc-pg-sw-3cls-ev3}, snapshot: \texttt{wli-searchdb-model5-2025-09-23-20-17})
    \item \textbf{3-class output:} \texttt{simple\_search\_prob} + \texttt{complex\_search\_prob} + \texttt{no\_search\_prob} = 1.0
    \item \textbf{Thresholds (evaluated in order):} \texttt{no\_search\_threshold} = 0.175, \texttt{complex\_search\_threshold} = 0.4, \texttt{simple\_search\_threshold} = 0 (catch-all)
    \item \textbf{First-turn override:} \texttt{force\_search\_first\_turn\_threshold} = 0.00001 (near-zero, almost always forces search on first message)
    \item \textbf{Enterprise vs.\ Personal divergence:} Enterprise has \texttt{prefetch\_threshold: null} + \texttt{passthrough\_tool\_calls: true}; Personal has \texttt{prefetch\_threshold: 0.55} + no passthrough tools
\end{itemize}

\paragraph{Note on the ``65\% search threshold'' claim:} Independent reverse-engineering by Resoneo documents a single \texttt{force\_search\_threshold} of 65\%. Our data captures a different classifier variant using a three-class threshold system rather than a single cutoff. The two may reflect different A/B variants or classifier versions. Our median \texttt{simple\_search\_prob} was 96.8\% --- far above any plausible boundary --- so we cannot empirically test where the effective decision point lies in the 50--70\% zone. The Resoneo-reported 65\% figure may also correspond to the \texttt{prefetch\_threshold} (0.55 in our data), which has shifted between versions.

\subsection{Freshness Steering}
\label{sec:freshness-steering}

\begin{itemize}
    \item \textbf{Gemini: Explicit Freshness Obsession:} \textbf{96.7\%} of Gemini runs (297/307 with valid grounding metadata) explicitly inject a year (2025 or 2026) into their fan-out queries. Of these, \textbf{74.3\%} (228/307) place the year signal in the very first query (Index 0), while a further \textbf{22.5\%} (69/307) include it only in later queries. Just \textbf{3.3\%} (10/307) of runs contained no year signal at all. This drives Gemini's aggressive ``Listicle Uptake'' --- by explicitly searching for ``Best [Product] 2025,'' the model forces the retrieval of time-stamped listicles, which then dominate its grounding.
    \item \textbf{GPT: Implicit Recency Reliance:} Only \textbf{5.1\%} of GPT runs use explicit year signals in their fan-out queries. GPT relies almost entirely on the search index's (Bing's) internal recency ranking, leading to a more diverse (though still listicle-leaning) grounding pool.
    \item \textbf{GPT's Multi-Turn Expansion:} GPT exhibits a ``Multi-Turn Fan-Out'' phenomenon where it issues secondary and tertiary queries (3+ queries) in response to initial results, effectively ``hunting'' for specific citations before finalizing the response. The empirical details of this mechanism are in Section~\ref{sec:multi-turn} below.
\end{itemize}

\paragraph{Key finding: The Sonic Classifier does NOT control re-search.} The correlation between \texttt{complex\_search\_prob} and multi-turn behavior is loose (avg 0.104 for multi-turn vs 0.025 for single-turn, but P050 re-searched at 0.3\% while P020 did not at 30.6\%). \paragraph{Observed patterns in Turn 2+ queries:}
Across all five multi-turn cases, Turn 2 queries tend to include specific product/service names (Jeenie, Boostlingo, ElevenLabs, Google Translate, Microsoft Translator, VEED, Kapwing) or rephrased terminology, whereas Turn 1 queries are more generic. We report this as an empirical observation without claiming a causal mechanism --- the model's internal decision to re-search is not visible in the network data.

\paragraph{Timing evidence:}
\begin{itemize}
    \item 4-query runs: second \texttt{web.run} fires \textasciitilde1.2 seconds after the first (time to receive and evaluate Turn 1 results)
    \item 6-query run (P073\_r3): calls are chained (\texttt{parent\_id} links form a sequential chain) with tight timing (484 ms $\rightarrow$ 341 ms) --- the model rapidly determined each round was insufficient
\end{itemize}

\paragraph{Query drift:} Across multiple runs of the same prompt, the fan-out query set can vary. This drift is a primary driver of stochastic retrieval---different fan-out sets lead to different retrieved sources and therefore different citations/recommendations.

\subsection{Implicit Localization Bias}
\label{sec:localization-bias}

\begin{itemize}
    \item \textbf{GPT Occurrence Rate:} Implicit localization signals (non-English fan-out queries generated from English prompts) were observed in \textbf{13.1\%} of GPT runs, distributed across three patterns:
    \begin{itemize}
        \item \textbf{Foreign-language anchoring} (30 runs): one of the two fan-out queries is issued in a non-English language (e.g., German, Turkish), with the other remaining in English.
        \item \textbf{Context-triggered} (9 runs): the prompt references an inherently local category (e.g., ``best pizza,'' ``local services''), triggering locale-aware query rewriting.
        \item \textbf{Untriggered anomalies} (23 runs): non-English fan-out queries appear with no obvious prompt-level trigger, suggesting IP/locale environment leaking into query generation.
    \end{itemize}
    \item \textbf{Gemini --- not observed via API:} Because our Gemini data was collected through the Vertex AI API (which does not carry IP or locale signals), we cannot test whether Gemini exhibits similar implicit localization. This remains a limitation; inspecting Gemini's consumer UI network traffic could reveal whether localization occurs there (see Section~2.4.2).
    \item \textbf{The ``English Anchor'' Effect (Gemini-specific):}
    \begin{itemize}
        \item Even for foreign-language prompts, Gemini \textbf{always} reserves the first grounding-support query slot (Index 0) for an English translation of the prompt.
        \item Due to the \textbf{First-Query Bias} (where models preferentially cite results from the first search query), the English-language search results dominate the final response.
        \item In 100\% of our localized Gemini runs, the cited sources were primarily global/English SaaS platforms and tech publications (e.g., \texttt{pcmag.com}, \texttt{techradar.com}), effectively creating a ``Global Information Bubble'' even for non-English users.
    \end{itemize}
    \item \textbf{Publisher/SEO$\rightarrow$GEO implication:} Even if users in non-English-speaking countries \textbf{search in English}, IP/locale-driven fan-out rewriting can route part of retrieval toward \textbf{localized-language SERPs}. Publishers without localized pages may lose visibility (and therefore citations/traffic) in these retrieval paths.
\end{itemize}

\paragraph{Bing's ``Elastic Page 1'' caveat:}
The global-rank table above treats every rank equally (all runs have results at Ranks 1--200). But in the actual Bing consumer UI, Page 1 is not a fixed ``Top 10'' --- it varies per scrape (see Section~2.2.1). Of 161 clean runs per tier (excluding \textasciitilde50 with a scraper artifact that tagged all 200 results as Page 1), the median Page 1 length was \textbf{6 results (Enterprise)} and \textbf{4 results (Personal)}. Nearly half of scrapes had 5 or fewer organic results on Page 1, and only about a third had the ``classic'' 8--10 results. This means the Rank 1--2 dominance in the table above is robust (every scrape has those ranks), but match rates at Ranks 5+ should be read with the caveat that many users would never see those results on Page 1.

\paragraph{Key observations on Bing rank bias:}
\begin{itemize}
    \item \textbf{Enterprise Rank 1--2 dominance}: 71\% and 69\% of runs cite the Bing \#1 and \#2 results. The drop to Rank 3 (40\%) is the steepest cliff in the data.
    \item \textbf{Personal is flat on Bing}: Rates range 12--27\% with no strong rank signal, consistent with Personal drawing citations primarily from Google.
    \item \textbf{The Page 2+ long tail}: Match rates at Ranks 11+ (the start of Page 2 for most scrapes) drop to single digits but never reach zero --- citations continue matching deep into the SERP, consistent with the page-level distribution in Section~\ref{sec:page-dist}.
\end{itemize}

\subsubsection{Key Observations on Provider Strategy}
\label{sec:provider-strategy}

\begin{itemize}
    \item \textbf{GPT Enterprise: The Bing Standard}: Consistent with OpenAI's Enterprise documentation, which explicitly names Bing as the search provider, we see an \textbf{81.3\% overlap} with the Bing index. Enterprise's Google overlap (27.8\%) serves as a \textbf{control baseline} --- since Enterprise does not retrieve from Google, this \textasciitilde28\% reflects natural domain overlap between the two indices (the same popular URLs appearing in both Bing and Google). Any Google overlap above this baseline in other tiers signals actual Google-sourced retrieval.
    \item \textbf{GPT Personal: The Multi-Provider Shift}: OpenAI's general documentation describes ChatGPT search as leveraging ``third-party search providers'' (plural). Our data confirms this: GPT Personal shows a much higher affinity for \textbf{Google (64.6\%)} than Enterprise (27.8\%), and achieves its highest coverage (\textbf{80.6\%}) when combining both indices.
    \item \textbf{The ``Google Jump'' (Enterprise vs.\ Personal)}: We observe a massive \textbf{36.8 percentage-point increase} in Google SERP overlap when moving from Enterprise (27.8\%) to Personal (64.6\%) accounts. This suggests that while Enterprise is ``locked'' to the Bing index for compliance/contractual reasons, the Personal account type has shifted to a Google-primary or multi-index retrieval strategy, significantly altering the ``Menu'' of available sources.
\end{itemize}

\label{sec:invisible-links}

    \item \textbf{Output}: \textbf{matched} vs \textbf{invisible} (unmatched).
    \item \textbf{Invisible rate (headline)}: use the \textbf{``Invisible (Missing)''} row in Section~\ref{sec:global-overlap} as the canonical rate.
    \item \textbf{Long tail context} (how deep ``matched'' links are): see Section~\ref{sec:page-dist} (Bing Pages 1--16).
\end{itemize}

\subsubsection{Operationalization: ``hidden zone'' vs ``truly invisible''}
\label{sec:hidden-vs-invisible}

We separate notions that are easy to conflate:

\begin{itemize}
    \item \textbf{Hidden zone (Bing Rank 11--30)}: a cited URL that is present, but beyond typical human scrolling.
    \begin{itemize}
        \item \textbf{GPT Enterprise}: \textbf{388 / 1,637 (23.7\%)} of cited occurrences were found in Bing \textbf{Rank 11--30}.
        \item \textbf{GPT Personal}: \textbf{326 / 1,839 (17.7\%)} of cited occurrences were found in Bing \textbf{Rank 11--30}.
    \end{itemize}
    \item \textbf{Truly invisible (Bing+Google control)}: cited URLs \textbf{not found in Bing $\leq$ 200} \textbf{and} \textbf{not found in Google} (SerpApi control for the same run).
    \begin{itemize}
        \item This matters for GPT Personal, which shows strong Google affinity; otherwise a Bing-only ``invisible'' count can overstate what is missing from the combined index surface.
    \end{itemize}
\end{itemize}

\subsubsection{Why these numbers are conservative (and what ``truly invisible'' likely means)}

Our reported invisible rates (16.3\% Enterprise, 19.4\% Personal) are \textbf{upper bounds} on truly index-absent citations. Two systematic factors inflate the invisible count:

\begin{enumerate}
    \item \textbf{The Rank 200 ceiling}: Our Bing scrape stops at Rank 200, but the page-level match histogram (see Section~\ref{sec:page-dist}) shows no convergence --- matches are still accumulating at Pages 15--16 with a smooth decay curve that does not reach zero. Scraping to Rank 300 or 400 would almost certainly recover additional matches, shrinking the invisible set. The ``invisible'' label for these URLs does not mean they are absent from Bing's index --- only that they fell beyond our scrape depth.

    \item \textbf{Bing Page 1 truncation (the ``Missing Middle'')}: As documented in Section~2.2.1 and Section~\ref{sec:rank1-effect}, nearly half of our Bing scrapes had 5 or fewer organic results on Page 1 due to UI-level pagination instability. Results that would normally rank at positions 3--7 can be dropped entirely from a truncated scrape --- they do not simply shift to Page 2. This is especially consequential because Page 1 is where we observe the \textbf{highest match rates} (69\% at Ranks 1--2, 40--46\% at Ranks 3--4; see Section~\ref{sec:rank1-effect}) --- so every result missed due to Page 1 truncation is statistically more likely to be a citation match than a result missed deeper in the index. These ``missing middle'' results are almost certainly available to ChatGPT through its backend API integration with Bing, which likely returns a clean, stable ranked list without the consumer UI's truncation artifacts. Some of our ``invisible'' citations may therefore be high-ranking Bing results that our scrape happened to miss.
\end{enumerate}

\textbf{If both factors were addressed} (deeper scraping + repeated Page 1 scrapes to capture the full elastic range), our overlap rates would likely increase and the remaining ``truly invisible'' set would converge toward citations that genuinely come from \textbf{outside the search index} --- sites like Wikipedia, app stores, and known reference domains that ChatGPT may access through parametric knowledge or supplementary indices rather than the fan-out search pipeline.

\subsection{Unreferenced Links --- The Search Pool Remainder}
\label{sec:unreferenced}

\section{Selection Drift (Enrichment-Based)}
\label{sec:selection-drift}

\textit{With the DNA profile established in Section~\ref{sec:content-dna}, we now measure how the model's selection (``Order'') systematically diverges from the available pool (``Menu'') along enriched feature dimensions.}

\textbf{Operational definitions} (matches \texttt{data/enrichment/full\_stratified\_drift\_report.txt}):
\begin{itemize}
    \item \textbf{Menu\% (feature at rank R)} = \% of retrieved candidates (for the baseline slice) at rank R with feature F.
    \item \textbf{Order\% (feature at rank R)} = \% of cited URLs that match into that same baseline slice at rank R with feature F.
    \item \textbf{Drift$_R$} = Order\% $-$ Menu\% (percentage points).
    \item \textbf{Volume-weighted drift} = $\sum_R \text{Drift}_R \cdot N^{\text{order}}_R \; / \; \sum_R N^{\text{order}}_R$.
\end{itemize}

\section{Listicle Extraction \& Bias Analysis}
\label{sec:listicle-bias}

\textit{Self-promotion, product text comparison, accuracy.}

\subsection{Scope: Solo-Cited Claims Only (Multi-Citation Filtering)}
\label{sec:solo-cited}

Listicle bias analysis requires attributing a product recommendation to a specific source. When a claim is backed by multiple citations (e.g., a listicle \textit{and} a product page), it becomes ambiguous which source drove the selection --- was the product picked because it appeared in the listicle, or because the model also had the vendor's own page? To avoid this attribution problem, the analyses in Sections~\ref{sec:self-promo}--\ref{sec:semantic-fidelity} are restricted to \textbf{solo-cited claims} (exactly one URL behind the claim).

This filtering excludes a non-trivial share of claims:
\begin{itemize}
    \item \textbf{GPT}: 458 / 4,296 claim occurrences (\textbf{10.7\%}) are multi-cited
    \item \textbf{Gemini}: 788 / 2,287 claim occurrences (\textbf{34.5\%}) are multi-cited
\end{itemize}

Among multi-cited claims involving at least one listicle, \textbf{\textasciitilde20\%} are mixed listicle+product-page citations (GPT: 21.1\%, Gemini: 19.6\%). Gemini's much higher multi-citation rate reflects its grounding architecture, which maps individual text segments to multiple \texttt{groundingChunks} --- producing richer but harder-to-attribute citation linkages.

The solo-cited filter is conservative: it discards cases where listicle influence may still be present but cannot be cleanly isolated. The trade-off is cleaner attribution at the cost of reduced sample size.

\subsection{Self-Promotion Bias \& Host Exclusion}
\label{sec:self-promo}

\begin{itemize}
    \item \textbf{Host exclusion (empirical)}: In the listicle semantic-fidelity audit (solo-cited listicles), models \textbf{often omit} the host's own product even when it is present in the listicle.
    \begin{itemize}
        \item \textbf{Gemini}: host present in \textbf{405} listicles; host \textbf{missing} in \textbf{71.9\%} (291/405), \textbf{included} in \textbf{28.1\%} (114/405)
        \item \textbf{GPT}: host present in \textbf{431} listicles; host \textbf{missing} in \textbf{63.6\%} (274/431), \textbf{included} in \textbf{36.4\%} (157/431)
    \end{itemize}
    \item \textbf{Bias multiplier (selection advantage)}: ``Missing most of the time'' does \textbf{not} imply ``no bias.'' When host is present, it is still selected at a rate far above a random item on the page.
    \begin{itemize}
        \item \textbf{Avg listicle size (in this audited subset)}: Gemini \textbf{8.1} products/page; GPT \textbf{9.3} products/page
        \item \textbf{Host selection rate}: Gemini \textbf{28.15\%}; GPT \textbf{36.43\%}
        \item \textbf{Random baseline} (approx $1/$avg products): Gemini \textbf{12.41\%}; GPT \textbf{10.70\%}
        \item \textbf{Bias multiplier}: Gemini \textbf{2.27$\times$}; GPT \textbf{3.40$\times$}
    \end{itemize}
    \item \textbf{Interpretation}: LLMs exhibit a mixed behavior: an ``anti-self-promo'' tendency (frequent host omission) combined with a measurable host selection advantage when they do pick items from host-authored listicles.
\end{itemize}

\subsection{Selection Order vs.\ Listicle Rank (The ``Re-Ranking'' Effect)}
\label{sec:reranking}

\begin{itemize}
    \item \textbf{Rank alignment}: how often \textbf{Chat response order} matches the \textbf{listicle's internal rank} for the same product (only when \texttt{listicle\_rank} is recoverable).
    \begin{itemize}
        \item \textbf{Gemini}: \textbf{29.5\%} (108/366)
        \item \textbf{GPT}: \textbf{27.9\%} (166/596)
    \end{itemize}
    \item \textbf{Interpretation}: models frequently \textbf{re-rank} listicle items in the final response. The listicle's ``\#1--\#10'' order is not preserved as the model's ``top picks'' order.
\end{itemize}

\paragraph{Listicle rank bias (top-item skew):} Do models preferentially pick items that are near the top of the cited listicle?

\begin{itemize}
    \item \textbf{Data used}: product roster items only where \texttt{present\_in\_listicle=="yes"} and \texttt{listicle\_rank} and \texttt{total\_products\_in\_listicle>1} are available.
    \begin{itemize}
        \item \textbf{GPT Enterprise}: \textbf{n=391} (mean listicle size \textbf{10.95})
        \item \textbf{GPT Personal}: \textbf{n=205} (mean listicle size \textbf{8.57})
        \item \textbf{Gemini}: \textbf{n=365} (mean listicle size \textbf{8.56})
    \end{itemize}
    \item \textbf{Observed share of selected items coming from top ranks}:
    \begin{itemize}
        \item \textbf{GPT Enterprise}: \#1 \textbf{18.9\%}, Top-3 \textbf{50.9\%}, Top-5 \textbf{76.0\%}

        \item \textbf{GPT Personal}: \#1 \textbf{2.34$\times$}, Top-3 \textbf{1.49$\times$}, Top-5 \textbf{1.22$\times$}

\subsection{Semantic Fidelity: Reading Comprehension vs.\ Attribution}
\label{sec:semantic-fidelity}

\begin{itemize}
    \item \textbf{The ``Two-Layer'' Grounding Problem:} We decompose ``Fidelity'' into two distinct measurable phenomena:
    \begin{enumerate}
        \item \textbf{Attribution Accuracy:} Does the cited source actually contain the product?
        \item \textbf{Reading Comprehension (Pure Fidelity):} When the product is present, how accurately does the model extract its details?
    \end{enumerate}
    \item \textbf{Key Findings (Solo-Cited Listicles):}
    \begin{itemize}
        \item \textbf{Pure Fidelity (Comprehension):} Both models exhibit near-perfect scores when the product is present (\textbf{Gemini: 4.81/5.0}, \textbf{GPT: 4.75/5.0}).
        \item \textbf{Attribution Failure:} Some ``solo-cited'' product claims still point to listicles where the product is not present (mis-attribution).
        \begin{itemize}
            \item \textbf{Gemini}: \textbf{7.36\%} (31/421 product roster items)
            \item \textbf{GPT}: \textbf{1.89\%} (13/689 product roster items)
        \end{itemize}
    \end{itemize}
    \item \textbf{Thesis Implication:} The ``hallucination problem'' in modern RAG systems is increasingly an \textbf{attribution/linkage problem}, not a ``reading'' or ``understanding'' problem. The models ``know'' the facts but ``forget'' which specific tab they were looking at when they found them.
\end{itemize}
