\chapter{Methodology \& Tools}
\label{ch:methodology}

This chapter describes the analytical tools and the instrumentation we used to study how ChatGPT and Gemini retrieve and cite web sources when answering product recommendation queries. ChatGPT prompts were run via the production web interface (\texttt{chatgpt.com}) and responses were captured via network payload inspection. We captured runs across two subscription tiers: \textbf{Personal} (a consumer ChatGPT Plus subscription) and \textbf{Business} (an organization-managed workspace account, provisioned through ChatGPT Business tier). All ChatGPT runs were done in Temporary Chat mode to prevent conversation history from influencing retrieval, and run with a U.S.\ proxy using a browser extension to prevent user location from affecting the results (Section~\ref{sec:proxy-requirement}). Gemini prompts were run via the Vertex~AI API (Gemini~3~Flash), which provides structured grounding metadata in JSON format.

The contrast between these three environments revealed notable differences, especially between the ChatGPT Plus and Business tiers. We ran each prompt three times per environment to examine how results vary across runs, which also increased our sample size. All prompts were executed between mid and late January 2026.

\section{Selection of the Research Query Set}
\label{sec:query-set-selection}

We have 79 unique prompts in our dataset that we have gathered from two platforms. 65 of these prompts were taken from Profound's Prompt Volumes feature \parencite{profound2026promptvolumes}, which provides prompt-level data derived from licensed and opt-in prompts of real ChatGPT users. Profound states that surfaced prompts may be rewritten for anonymity or clarity, so these are representative of real user intent. The other 14 prompts were taken from Ahrefs' AI Citations feature \parencite{ahrefs2025aicitations}, which we have used to capture additional prompts within our target verticals. Prompts span collection dates from January 2025 to January 2026, with the majority concentrated between July and December 2025.

From the available prompts, we filtered for product discovery queries with commercial intent---prompts where users ask for tool recommendations, comparisons, or ``best of'' lists---as these are the queries most likely to trigger web search grounding (see Section~\ref{sec:commercial-catalyst}).
All queries are in the AI speech and language technology sector
(speech-to-text, live transcription, voice translation, text-to-speech).
This domain focus reflects the author's professional expertise in this vertical,
which allowed the author to assess retrieval relevance and spot citation errors
that a domain outsider might miss. While 79 prompts is modest compared to large-scale observational studies, each prompt was run 3 times across 3 environments (711 total runs), producing over 2{,}000 fan-out queries---each scraped on both Bing (to Rank~200) and Google---and approximately 12{,}000 total citations to analyze. Scaling beyond this would have been impractical given the per-query scraping and enrichment costs.

\paragraph{Prompt categories.}
The 79 prompts fall into 4 categories:
\begin{itemize}
  \item Live/real-time translation (25 prompts, 31.6\%) ---
    e.g.\ \emph{``Is there a Windows application for live translation
    during calls in Google Meet?''}
  \item Post-production translation (24, 30.4\%) ---
    e.g.\ \emph{``Which free AI would you recommend for translating my video?''}
  \item Post-production transcription / speech-to-text (21, 26.6\%) ---
    e.g.\ \emph{``Is there a transcription software available for a one-time payment
    instead of a subscription?''}
  \item Text-to-speech (9, 11.4\%) ---
    e.g.\ \emph{``Can you recommend free text-to-speech extensions
    that don't sound robotic?''}
\end{itemize}

Of the 79 prompts, 72 are in English and 7 are in foreign languages (1~French, 1~Chinese, 2~Turkish, 1~German, 1~Italian, 1~Spanish). All 7 foreign-language prompts originated from Ahrefs; the Profound-sourced prompts were exclusively English. We included the foreign-language prompts to introduce variance in retrieval behavior; their effects on how the models retrieve and cite sources are analyzed in Section~\ref{sec:localization-bias}.
\label{sec:localization}

All ChatGPT runs and Bing scrapes were routed through a US-based proxy to

\section{Anatomy of a ChatGPT Response}
\label{sec:chatgpt-anatomy}

\subsection{Search Trigger}
\label{sec:pipeline-overview}
\label{sec:search-trigger-method}

When a user submits a prompt, the first thing ChatGPT decides is whether to search the web at all. Figure~\ref{fig:searching-web} shows what the user sees when the system commits to searching: a brief ``Searching the web'' indicator before any results appear.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.75\textwidth]{figures/searching_web.png}
\caption{ChatGPT's ``Searching the web'' indicator as seen by the user.}
\label{fig:searching-web}
\end{figure}

Behind this indicator, our network instrumentation captured the full search pipeline from the \texttt{conversation} endpoint's event stream. Figure~\ref{fig:network-response} shows this stream as seen in Chrome DevTools: the \texttt{conversation} endpoint (selected in the left panel) returns a streamed response containing search invocations, \texttt{tool:web} calls, and search results with titles and snippets.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{figures/network_response.png}
\caption{Chrome DevTools Network tab with the \texttt{conversation} endpoint selected (left panel), showing the streamed response containing search invocations, \texttt{tool:web} calls, and returned search results with titles and snippets.}
\label{fig:network-response}
\end{figure}

The stream contains the classifier output (\texttt{sonic\_classification\_result}), fan-out queries, search results, and citation mappings. One caveat: the \texttt{web\_search\_triggered} boolean flag proved unreliable---some runs reported \texttt{false} despite containing \texttt{web.run} calls and search results. We therefore determined search status by checking for the presence of \texttt{web.run} tool calls rather than trusting the flag. The full classifier configuration is reported in Section~\ref{sec:search-trigger}.

\subsection{Fan-Out Queries}
\label{sec:fan-out-queries}

Once the search trigger fires, ChatGPT does not search for the user's prompt verbatim. Instead, it rewrites the prompt into one or more targeted search queries \parencite{openai2024search}---commonly referred to as \emph{fan-out queries}. As Figure~\ref{fig:fan-out-ui} shows, the UI exposes only one of them (``Searching for best app for voice translation''). Our network instrumentation reveals that a second query is always dispatched in parallel but never shown to the user; both are captured in the \texttt{search\_model\_queries} field.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.75\textwidth]{figures/fan_out_query.png}
\caption{The single fan-out query visible in ChatGPT's UI. A second query is always dispatched but hidden in the interface.}
\label{fig:fan-out-ui}
\end{figure}

Figure~\ref{fig:fanout-raw} shows the raw \texttt{search\_model\_queries} object from the network stream containing the query pair, and Figure~\ref{fig:sonicberry} shows the \texttt{web.run} tool call that dispatches them. The model can issue multiple \texttt{web.run} calls per run; the distribution is reported in Section~\ref{sec:multi-turn}.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth]{figures/fan_out.png}
\caption{Fan-out query pair as seen in the raw network event stream: the \texttt{search\_model\_queries} object contains the two reformulated queries.}
\label{fig:fanout-raw}
\end{figure}

The results from these queries form the full retrieval pool, captured in the \texttt{search\_result\_groups}
 field, which contains the URL, title, snippet, and 
 publication date for each candidate. To determine which of these candidates were actually cited, we reconstruct the citation-to-source mapping from \texttt{content\_references}, which records the start index of each citation token in the streamed response text. The full mapping pipeline is described in Section~\ref{sec:claim-to-link}. A glossary of all network payload fields we captured is provided in Appendix~\ref{app:network-glossary}.

\subsection{Citation Mapping}
\label{sec:citation-mapping}
\label{sec:claim-to-link}

Each inline citation chip in the response corresponds to a token in the network stream (e.g., \texttt{citeturn0search9}). The \texttt{content\_references} field records the \texttt{start\_idx} and \texttt{end\_idx} of each token, letting us map every citation back to the exact span of response text it covers and, via the \texttt{ref\_id} key, to the source URL in \texttt{search\_result\_groups}. Figure~\ref{fig:claim-extraction} shows this mapping in practice.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{figures/run_viewer_citation_claim.png}
\caption{Citation-to-source mapping from the Data Viewer (a per-run inspection tool built for this study; see Section~\ref{sec:analysis-applications}). The top panel highlights citation tokens inline within the response text. The bottom table resolves each token to its claim text, target URL, and character offsets.}
\label{fig:claim-extraction}
\end{figure}

Some citation chips bundle multiple sources under a single display, indicated by a ``+1'' or ``+2'' suffix (shown as the \textcolor{orange}{orange} popup in Figure~\ref{fig:chatgpt-anatomy}). In the network stream, these appear as concatenated tokens (e.g., \texttt{turn0search8} + \texttt{search15}), meaning a single text span is grounded by two or more URLs. Multi-cited claims are reported further in Section~\ref{sec:solo-cited}.

\subsection{Key Differences in Instrumentation}
\label{sec:gemini-instrumentation-differences}

Unlike ChatGPT, where we had to extract citation tokens from the network stream and stitch them back together with character offsets (Section~\ref{sec:citation-mapping}), Gemini provides the segment-to-source mapping directly in its API response via \texttt{groundingSupports}. One practical challenge is that \texttt{groundingChunks} contain Vertex redirect URLs rather than raw destination URLs; we built a resolution script to follow each redirect and recover the actual domain.

We used Gemini~3.0~Flash, the most recent model (at the time of this research) that Google serves as the default on \texttt{gemini.google.com}. All runs used the minimum thinking budget available on the API, which made retrieval behavior easier to observe and kept fan-out counts relatively lower. Even at minimum thinking, Gemini occasionally produced up to 8 fan-out queries across multiple search turns, compared to ChatGPT's typical 2 per run.

All Gemini data was collected via the Vertex~AI API. Inspecting the Gemini consumer UI with a similar methodology to what we did for ChatGPT might give results that are more comparable, but we chose to use the API due to its convenience and reliability. This remains a potential avenue for future work (Section~\ref{sec:lim-gemini}).

\section{Search Engine Baselines}
\label{sec:serp-baselines}

To measure how much LLM citations overlap with conventional search results, we collected SERP baselines from both Google and Bing for the 2{,}280 fan-out queries generated across our 711 runs.

\subsection{Search Engine Scraping Challenges}
\label{sec:ethical-legal}
\label{sec:structural-pivot}

One of the biggest challenges in this study was accessing raw search indices programmatically. On August~11, 2025, Microsoft retired public access to the Bing Search API. This forced us to scrape Bing's consumer UI
 via a browser extension (Section~\ref{sec:bing-scraping}), which introduced its own challenges (Section~\ref{sec:bing-pagination-instability}). Running the extension through a 
 US-based proxy, we encountered no rate-limiting issues from Bing.

Scraping Google results proved to be more difficult. Our initial attempts at scraping Google directly through a browser extension were met with escalating CAPTCHAs and rate limiting; the frequency of these challenges gradually increased until it became apparent that direct scraping would not be a feasible methodology for a study of this size. We therefore turned to SerpApi, a third-party scraping service that routes requests through residential proxies. We configured all SerpApi calls with a United States location parameter to align with the US-based proxy used for our ChatGPT and Bing scraping (Section~\ref{sec:proxy-requirement}).

SerpApi itself has faced legal challenges because of this service they provide. On December~19, 2025, Google filed a lawsuit against SerpApi, alleging unlawful scraping and circumvention of security measures\footnote{\url{https://blog.google/innovation-and-ai/technology/safety-security/serpapi-lawsuit/}}. The SerpApi homepage has historically listed major AI players including Perplexity and OpenAI as customers; \textcite{theinformation2025openaiserpapi} reported that OpenAI used SerpApi to extract Google results for powering ChatGPT responses. In September~2025, Google also confirmed it no longer supports the \texttt{num} parameter that previously allowed retrieving up to 100 results per page, forcing all consumers of Google Search to paginate one page at a time \parencite{searchengineland2025num100}. This change means that anyone looking to scrape Google at scale would require more resources, such as the additional API credits we spent on SerpApi. It may also reflect a broader effort by Google to limit competitors from scraping its data to fuel their own LLMs.

The companies building RAG systems rely on third-party scrapers to access the live web, while the search engines are actively closing off that access. As scraping becomes more restricted, studies like this one will become harder to replicate.

\subsection{Google SERP Baseline}
\label{sec:google-serp-types}

Our Google SERP baseline was collected via SerpApi, which returns results in multiple \texttt{result\_type} buckets: organic results (standard search results), video results (often YouTube-heavy), discussion/forum blocks, and People Also Ask (\texttt{related\_question}) entries. For each query, we paginated SerpApi until at least 20 organic results were collected; in practice, this typically required 3 pages, yielding approximately 25 organic results per query. The total result count per query is higher when including the non-organic types. This Google baseline serves as the primary overlap surface for the Gemini study. Since OpenAI confirms that Enterprise and Edu workspaces use Bing exclusively as their search provider \parencite{openai2024enterprise}, Google also serves as a control group for the ChatGPT Business study, and as a third-provider verification for ChatGPT Personal---allowing us to test whether citations that do not appear in Bing can be found in Google instead (Section~\ref{sec:citation-overlap}).

\subsection{Bing SERP Scraping}
\label{sec:bing-scraping}

With no official Bing API available (Section~\ref{sec:structural-pivot}), we initially tested SerpApi's Bing endpoint, but found that results beyond the first page were highly irrelevant, mirroring the pagination instability we later documented (Section~\ref{sec:bing-pagination-instability}). We therefore used a Chrome browser extension originally forked from a related study \parencite{cirac2025bingscraper} and substantially modified for our requirements. The extension scrapes Bing's live consumer UI by simulating human search interaction: typing queries with randomized delays, clicking the search button through DOM, and waiting for the page to stabilize before extracting results.

Organic results are separated from ads by filtering on Bing's ``Sponsored'' tags. For each result, the extension extracts position, title, URL, domain, snippet, and page number. Tracking parameters (\texttt{utm\_*}, \texttt{fbclid}, \texttt{gclid}, etc.) are stripped to normalize URLs for overlap matching. The extension paginates until at least 200 results are collected per query ($\sim$20 pages), with delays between pages. All Bing scrapes were routed through a US-based proxy to match the retrieval environment used for ChatGPT runs (Section~\ref{sec:proxy-requirement}).

\subsection{Why We Scraped Bing to Rank~200}
\label{sec:methodological-evolution}

We detail this section extensively because getting an accurate representation of what ChatGPT looks at from Bing Search was important for our study. Our Google baseline stops at $\sim$25 organic results per query (Section~\ref{sec:google-serp-types}); initially we scraped a similar Top~30 for Bing. This yielded only a 40.3\% citation overlap, which we felt was too low. We then discovered that the ``Searching for\ldots'' text in the UI (Figure~\ref{fig:fan-out-ui}) only surfaces one of the two fan-out queries ChatGPT sends per search turn (Section~\ref{sec:pipeline-overview}), meaning our initial scrapes were matching against an incomplete query set.

After re-running with both fan-out queries, our Data Viewer (Figure~\ref{fig:data-viewer}) still showed a significant visibility gap: ChatGPT was citing relevant pages completely absent from the Top~30. This prompted us to look more closely into how Bing's search interface behaves.

In the first scrape (Table~\ref{tab:bing-full}), Page~1 returned 7 tightly relevant video translation tools. Page~2 was already noticeably weaker: alongside relevant results like \texttt{maestra.ai} (AI Video Translator) and \texttt{notegpt.io} (AI Audio Translator), it included off-topic pages such as \texttt{pdftranslate.ai} (PDF translation) and \texttt{notegpt.io} (YouTube Video Summarizer).

The second scrape of the same query (Table~\ref{tab:bing-truncated}) we ran right after returned
 only 2 organic results on Page~1: \texttt{zeemo.ai} and \texttt{wayin.ai}. This was consistent with the first run
 but the remaining 5 results (ranks 3--7, bolded in Table~\ref{tab:bing-full}) did not shift to Page~2 as we have expected.
 Page~2 showed a similar mix of relevant and off-topic results, including \texttt{a2e.ai} (uncensored AI videos) and \texttt{dreamfaceapp.com} (image generation).

We observed four patterns from this and subsequent scrapes:

\begin{enumerate}
    \item \textbf{Page~1 results can be lost entirely.} Bing's Page~2 appears to start from a fixed offset regardless of how many organic results Page~1 actually displayed. When Page~1 is compressed by ads or carousels---which happened in the majority of our scrapes (Table~\ref{tab:bing-page1-size})---the displaced results do not shift to Page~2. This is significant because Page~1 is where we expect the highest citation overlap with ChatGPT.
    \item \textbf{Page~2 is disproportionately noisy.} Off-topic and irrelevant results concentrate on Page~2 far more than its position would suggest. Our overlap data confirms this: Page~2 citation-match rates were comparable to Page~8- (Section~\ref{sec:page-dist}).
    \item \textbf{Pages~3+ are more predictable.} From Page~3 onward, results followed a more consistent pattern, though irrelevant results still appeared occasionally. Our citation-overlap data corroborates this: after Page~3 we see a gradual decay in relevancy. (Section~\ref{sec:page-dist}).
    \item \textbf{Matches continued deep into the results.} We kept finding citation matches well past Rank~150.
    If Bing's backend index is properly ordered---which it likely is through
     its internal API---these results could fit in a tightly ranked Top~30 instead of being scattered across 200.
\end{enumerate}

Because of these findings we expanded our Bing scrapes to Rank~200 to compensate for UI-layer instability and
 recover matches that a stable API would have probably returned in the Top~10--30. Our page-level distribution data (Section~\ref{sec:page-dist}) shows
 that citation matches do not reach zero at Pages~15--16 but continue with a smooth decay curve. 
Extending to Rank~300 or beyond would recover additional matches with diminishing returns, further narrowing the ``truly invisible'' set (see Section~\ref{sec:fw-deeper-crawling}).

\subsubsection{The Retirement of the Bing Search API}

Microsoft retired public access to the Bing Search API in August~2025
(Section~\ref{sec:structural-pivot}). Since then, the programmatic consumers of
Bing's index are backend partners like OpenAI or Microsoft's own AI Agents infrastructure
 \footnote{\url{https://learn.microsoft.com/en-us/azure/ai-foundry/agents/how-to/tools-classic/bing-grounding}}.
  This leaves little incentive for Microsoft to maintain stable consumer pagination at depth since 
  human users rarely paginate past Page~1.
   Our approach is therefore a proxy for 
   what ChatGPT actually sees. 
\section{Analysis Applications}
\label{sec:analysis-applications}

Prior studies have analyzed LLM citation overlap at scale---\textcite{ong2025chatgptgoogle} processed over 
100,000 fan-out queries---but without per-run inspection tools, patterns in the data can go unnoticed. 
 This is why we built a viewer application that recreates the ChatGPT interface for 
 each captured run. 
 
The prompt, the full response with inline citations, 
 and the Bing and Google search results for that run's
  fan-out queries side by side (Figure~\ref{fig:data-viewer}). 
  Overlapping results are color-coded: green for Bing matches, yellow for Google matches. The viewer also shows how many of the run's cited links are covered by each SERP baseline and breaks down overlap contribution per fan-out query. This let us go through runs one by one and look for patterns.
 The viewer also includes aggregate dashboards for 
 overlap statistics, domain-level exploration, and breakdowns of truly invisible URLs (Section~\ref{sec:top-invisible-domains}) across all runs. We built a similar tool for Gemini, comparing grounding chunks and supports against the Google SERP baseline. Both tools were used throughout the analysis reported in Chapter~\ref{ch:findings}.

\section{Content DNA Enrichment}
\label{sec:content-dna}

Knowing which URLs were cited was not enough; we also needed to know what kind of pages they are, so we could understand what features lead to the citation decision. We built a pipeline that labels every URL in our dataset with a structural profile which we call its Content DNA. This profile includes page type (listicle, product page, documentation), whether the page has tables, numbered lists, or pros/cons sections, and how fresh the content is (Figure~\ref{fig:dna-snip}).

\begin{figure}[htbp]

\label{sec:labeling-pipeline}
\label{sec:labeler-fidelity}

We built an automated pipeline using GPT-5-mini and Gemini~2.5~Flash to label each URL's structural characteristics. The pipeline works in three stages:

\begin{enumerate}
    \item \textbf{Fetch.} Raw HTML is downloaded for each URL and converted to clean text.
    \item \textbf{Label.} The LLM reads the page and assigns labels for page type, structural features, and freshness, as shown in Figure~\ref{fig:dna-snip}. The full labeling prompt is in Appendix~\ref{app:dna-prompt}.
    \item \textbf{Audit.} A subset of labels was manually checked, focusing on the distinction between product landing pages and editorial blogs.
\end{enumerate}

To verify that labels are not model-dependent, we had GPT-5-mini and Gemini~2.5~Flash each label all 6{,}000+ URLs and compared their outputs against each other. Agreement was 91--95\% on structural fields (tables, numbered lists, pros/cons, authorship, citations) and 88--92\% on categorical fields (page type, format).

Well-known domains with fixed structures such as Reddit, Wikipedia, app stores, and YouTube were excluded from LLM labeling and assigned defaults instead. Our structural analyses in Chapter~\ref{ch:findings} therefore focus on pages the pipeline identified as product pages and listicles, where these features are meaningfully present.

\section{Use of AI Tools in This Research}

This study used large language models at every stage, and we disclose their role for transparency.

AI tools were also used for proofreading, structural editing, and \LaTeX{} formatting, with Claude Code and OpenAI Prism used at different stages.
