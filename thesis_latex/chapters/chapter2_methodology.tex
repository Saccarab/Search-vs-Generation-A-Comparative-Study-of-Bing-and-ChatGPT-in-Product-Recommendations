\chapter{Methodology \& Tools}
\label{ch:methodology}

This chapter describes the analytical tools and the instrumentation we used to study how ChatGPT and Gemini retrieve and cite web sources when answering product recommendation queries. ChatGPT prompts were run via the production web interface (\texttt{chatgpt.com}) and responses were captured via network payload inspection. We captured runs across two subscription tiers: \textbf{Personal} (a consumer ChatGPT Plus subscription) and \textbf{Business} (an organization-managed workspace account, provisioned through ChatGPT Business tier). All ChatGPT runs were done in Temporary Chat mode to prevent conversation history from influencing retrieval, and run with a U.S.\ proxy using a browser extension to prevent user location from affecting the results (Section~\ref{sec:proxy-requirement}). Gemini prompts were run via the Vertex~AI API (Gemini~3~Flash), which provides structured grounding metadata in JSON format.

The contrast between these three environments revealed notable differences, especially between the ChatGPT Plus and Business tiers. We ran each prompt three times per environment to examine how results vary across runs, which also increased our sample size.

\section{Selection of the Research Query Set}
\label{sec:query-set-selection}

We have 79 unique prompts in our dataset that we have gathered from two platforms. 65 of these prompts were taken from Profound's Prompt Volumes feature \parencite{profound2026promptvolumes}, which provides prompt-level data derived from licensed and opt-in prompts of real ChatGPT users. Profound states that surfaced prompts may be rewritten for anonymity or clarity, so these are representative of real user intent. The other 14 prompts were taken from Ahrefs' AI Citations feature \parencite{ahrefs2025aicitations}, which we have used to capture additional prompts within our target verticals. Prompts span collection dates from January 2025 to January 2026, with the majority concentrated between July and December 2025.

From the available prompts, we filtered for product discovery queries with commercial intent
prompts where users ask for tool recommendations, comparisons, or ``best of'' lists.
as are the queries most likely to trigger web search grounding
(see Section~\ref{sec:commercial-catalyst}).
All queries are in the AI speech and language technology sector
(speech-to-text, live transcription, voice translation, text-to-speech).
This domain focus reflects the author's professional expertise in this vertical,
which allowed the author to assess retrieval relevance and spot citation errors
that a domain outsider might miss.

\section{Retrieval Environment}
\label{sec:proxy-requirement}

All ChatGPT runs and Bing scrapes were routed through a US-based proxy to prevent IP geolocation from influencing retrieval results (Section~\ref{sec:localization-bias}). SerpApi calls for the Google SERP baseline (Section~\ref{sec:google-serp-types}) were similarly configured with a US location parameter. The US baseline aligns with the globally available AI/SaaS products in our query set, where the US-English SERP is the most relevant ground truth.

\section{Anatomy of a ChatGPT Response}
\label{sec:chatgpt-anatomy}

\subsection{Search Trigger}
\label{sec:pipeline-overview}
\label{sec:search-trigger-method}

When a user submits a prompt, the first thing ChatGPT decides is whether to search the web at all. Figure~\ref{fig:searching-web} shows what the user sees when the system commits to searching: a brief ``Searching the web'' indicator before any results appear.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.75\textwidth]{figures/searching_web.png}
\caption{The first visible indicator of the retrieval pipeline: ChatGPT displays ``Searching the web'' before any fan-out queries or results are shown to the user.}
\label{fig:searching-web}
\end{figure}

Behind this indicator, our network instrumentation captured the search-trigger decision via the \texttt{sonic\_classification\_result} field in the event stream. This field contains a classifier output with probabilities (\texttt{simple\_search\_prob}, \texttt{complex\_search\_prob}) and thresholds that determine whether the prompt warrants a web search. The event stream also includes \texttt{web\_search\_triggered} (whether search actually ran) and \texttt{web\_search\_forced} (whether search was forced regardless of classifier output). The full classifier configuration and its behavior are reported in Section~\ref{sec:search-trigger}.

\subsection{Fan-Out Queries}
\label{sec:fan-out-queries}

Once the search trigger fires, ChatGPT does not search for the user's prompt verbatim. Instead, it generates its own search queries behind the scenes---commonly referred to as \emph{fan-out queries}. As Figure~\ref{fig:fan-out-ui} shows, the UI exposes only one of them (``Searching for best app for voice translation''). Our network instrumentation reveals that a second query is always dispatched in parallel but never shown to the user; both are captured in the \texttt{search\_model\_queries} field.

\begin{figure}[htbp]
\centering
\includegraphics[width=0.75\textwidth]{figures/fan_out_query.png}
\caption{ChatGPT exposes only one fan-out query in the UI. Network instrumentation reveals that a second query is always dispatched in parallel but never shown to the user.}
\label{fig:fan-out-ui}
\end{figure}

Each pair of fan-out queries is dispatched via a tool call named \texttt{web.run}. In 94\% of our runs, we observed a single \texttt{web.run} call that produces 2 queries. On remainder of our runs, we observed that model will do additional web.run calls and create more fan outs query pairs. The distribution of search turns and query strategies are reported in Section~\ref{sec:multi-turn}.

The results from these queries form the full retrieval pool, captured in the \texttt{search\_result\_groups} field, which contains the URL, title, snippet, and publication date for each candidate (the publication date field is populated for roughly half of all entries; its potential as a selection signal is discussed in Section~\ref{sec:fw-pub-date}). To determine which of these candidates were actually cited, we reconstruct the citation-to-source mapping from \texttt{content\_references}, which records the start index of each citation token in the streamed response text. The full mapping pipeline is described in Section~\ref{sec:claim-to-link}. A glossary of all network payload fields we captured is provided in Appendix~\ref{app:network-glossary}.

\subsection{Citation Mapping}
\label{sec:citation-mapping}
\label{sec:claim-to-link}

Each inline citation chip in the response corresponds to a token in the network stream (e.g., \texttt{citeturn0search9}). The \texttt{content\_references} field records the \texttt{start\_idx} and \texttt{end\_idx} of each token, letting us map every citation back to the exact span of response text it covers and, via the \texttt{ref\_id} key, to the source URL in \texttt{search\_result\_groups}. Figure~\ref{fig:claim-extraction} shows this mapping in practice.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{figures/run_viewer_citation_claim.png}
\caption{Citation-to-source mapping from the Data Viewer (a per-run inspection tool built for this study; see Section~\ref{sec:analysis-applications}). The top panel highlights citation tokens inline within the response text. The bottom table resolves each token to its claim text, target URL, and character offsets.}
\label{fig:claim-extraction}
\end{figure}

Some citation chips bundle multiple sources under a single display, indicated by a ``+1'' or ``+2'' suffix (shown as the \textcolor{orange}{orange} popup in Figure~\ref{fig:chatgpt-anatomy}). In the network stream, these appear as concatenated tokens (e.g., \texttt{turn0search8} + \texttt{search15}), meaning a single text span is grounded by two or more URLs. The multi-cited claims is reported further in Section~\ref{sec:solo-cited}.

\subsection{Key Differences in Instrumentation}
\label{sec:gemini-instrumentation-differences}

The most significant difference is transparency: Gemini is ``grounding-first'': it exposes the source URLs it retrieved and maps specific response segments back to those sources via \texttt{groundingSupports}, enabling higher-resolution fidelity analysis than ChatGPT's output-side-only instrumentation allows. However, Gemini does not expose the raw page text it ingested; we see which URLs were used and which response segments they support, but not the actual snippets the model read from each page.

A practical challenge is that Gemini's \texttt{groundingChunks} do not expose raw URLs; instead, they contain internal redirect URLs (e.g., \texttt{vertexaisearch.cloud.google.com/\ldots}) that must be followed to discover the actual destination domain. We built a dedicated resolution script that collects all unique Vertex redirect URLs, follows each via HTTP, and produces a Vertex URL $\rightarrow$ resolved destination mapping. Redirects that failed programmatically (due to timeouts or anti-bot blocks) were resolved via a custom Chrome extension (\texttt{VertexResolverExtension}) that opens each URL in a background tab and captures the final destination. Without this resolution step, no domain-level or overlap analysis would be possible on the Gemini data.

All Gemini runs used the minimum thinking budget available via the API. Even at minimum thinking, Gemini occasionally issued multiple rounds of fan-out queries; higher thinking budgets amplify this effect, producing longer retrieval chains. Our use of minimum thinking keeps the fan-out count bounded and comparable across runs, but means the study captures baseline retrieval behavior rather than maximum-depth grounding capability.

Finally, our Gemini data comes entirely from the Vertex~AI API, which provides structured grounding metadata but does not carry IP or locale signals. Inspecting the Gemini consumer UI (\texttt{gemini.google.com}) via network packet analysis, mirroring our ChatGPT instrumentation approach, could reveal additional signals not exposed in the API. This remains a potential avenue for future work (Section~\ref{sec:fw-perplexity-aio}).

\section{Search Engine Baselines}
\label{sec:serp-baselines}

With the ChatGPT and Gemini instrumentation established, we now describe the search engine baselines against which we measure citation overlap. These baselines answer the question: are the URLs these models cite also present in conventional search results for the same queries?

\subsection{Google SERP Baseline (SerpApi)}
\label{sec:google-serp-types}

Our Google SERP baseline was collected via SerpApi, which returns results in multiple \texttt{result\_type} buckets: organic results (standard web listings), video results (often YouTube-heavy), and discussion/forum blocks. For each query, we paginated SerpApi until at least 25 organic results were collected; in practice, this typically required approximately 3 pages of results. This ``Top-25 Organic'' baseline serves as the Google control surface against which we measure citation overlap, complementing the deeper Bing Top-200 scrape described below.

\subsection{Bing SERP Scraping (Browser Extension)}
\label{sec:bing-scraping}

Because Microsoft retired public Bing Search API access on August~11, 2025 (see Section~\ref{sec:structural-pivot}), no stable programmatic API was available for academic SERP collection. We therefore used a Chrome browser extension (\texttt{tools/Bing Results Scraper}) that scrapes Bing's live consumer UI via DOM interaction. The extension runs as a Manifest~V3 content script that simulates human search interaction: typing queries character-by-character with randomized inter-key delays (10--50\,ms), clicking the search button, and waiting for DOM stabilization (result count checked across 3 consecutive iterations before proceeding).

Organic results are isolated from ads using a multi-layer filtering approach. The primary selector (\texttt{.b\_algo:not(.b\_adTop):not(.b\_adBottom):not([data-apurl])}) is supplemented by a secondary function that checks DOM class markers, text-prefix matching (\texttt{/\^{}Sponsored\textbackslash b/i}), CSS \texttt{::before} pseudo-element inspection, and URL-based filtering of known ad-click endpoints. Unresolved Bing redirect URLs (\texttt{bing.com/ck/}) are discarded as probable ads. For each result, the extension extracts position, title, URL, domain, display URL, snippet, and page number; Bing's redirect-wrapped URLs are decoded via URL-parameter extraction with Base64 and hex-byte fallback, and tracking parameters (\texttt{utm\_*}, \texttt{fbclid}, \texttt{gclid}) are stripped to normalize URLs for overlap matching.

The extension paginates through 20 pages of results ($\sim$10 organic results per page = Rank~200 per query), with 3-second waits between pages and positions numbered strictly sequentially across pages. All Bing scrapes were routed through a US-based proxy to match the retrieval environment used for ChatGPT runs (see Section~\ref{sec:proxy-requirement}), ensuring that localized SERP variation does not inflate or deflate overlap measurements.

\subsection{Ethical and Legal Constraints}
\label{sec:ethical-legal}

A significant challenge in RAG research is the increasing difficulty of accessing raw search indices. On December~19, 2025, Google filed a lawsuit against SerpApi, the same service we used for our Google SERP baseline (Section~\ref{sec:google-serp-types}), alleging unlawful scraping and circumvention of security measures\footnote{\url{https://blog.google/innovation-and-ai/technology/safety-security/serpapi-lawsuit/}}. The SerpApi homepage has historically listed major AI players including Perplexity and OpenAI (the latter subsequently removed) as customers\footnote{\url{https://serpapi.com/}}, suggesting a complex ecosystem where the very companies building RAG systems may rely on third-party scrapers to access the live web. This legal pressure has led to concrete technical restrictions: in September~2025, Google confirmed it no longer supports the \texttt{num} parameter that previously allowed retrieving up to 100 results per page, forcing all consumers of Google Search to paginate through results one page at a time \parencite{searchengineland2025num100}. These developments further justify our Deep Hunt (Rank~200) methodology: as traditional scraping becomes more restricted, the visibility gap between what an LLM can see (via direct API access) and what a researcher can see (via public search UIs) will likely widen.

\section{Methodological Evolution: From Top~30 to ``Deep Hunt'' (Rank~200)}
\label{sec:methodological-evolution}

Our scrape depth evolved through three stages as the study uncovered progressively more of ChatGPT's retrieval architecture. The initial design used only the single fan-out query visible in ChatGPT's UI (the ``Searching for\ldots'' text) and scraped the Top~30 Bing results for each, yielding a 40.3\% citation overlap. At this stage we had no knowledge of the hidden double fan-out mechanism; we assumed the UI-displayed query was the only query issued.

The first turning point came with network instrumentation (Section~\ref{sec:pipeline-overview}). Capturing raw event-stream payloads revealed that ChatGPT always dispatches \emph{two} fan-out queries per search turn, not one; the ``Searching for\ldots'' text surfaces only one of them. This meant our initial scrapes were matching against an incomplete query set, systematically understating true overlap. Even after correcting for the double fan-out, qualitative review using our custom Data Viewer (Figure~\ref{fig:data-viewer}) revealed a persistent visibility gap: ChatGPT was citing high-quality, relevant pages that were completely absent from the Top~30 human-facing results.

\begin{figure}[htbp]
\centering
\includegraphics[width=\textwidth]{figures/data_viewer.png}
\caption{The Data Viewer built for this study, showing run P001\_r2 (Personal tier). \textbf{Left panel:} the ChatGPT response with inline citation badges showing each cited domain and its Bing rank. \textbf{Right panel:} the SERP overlap screen, listing scraped Bing results alongside the model's citations.}
\label{fig:data-viewer}
\end{figure}

To test whether these citations were truly ``invisible'' or merely ``buried,'' we expanded to a Deep Hunt at Rank~200. Many citations did appear at depth: Bing surfaces the exact pages ChatGPT cites, but at ranks well beyond typical human scrolling. However, the poor relevance and instability of results beyond Page~1 (see Section~\ref{sec:bing-pagination-instability}) suggest that Bing's consumer UI may not maintain a tightly curated ranked list beyond the first page.

Even Rank~200 may not be sufficient. Our page-level distribution data (Section~\ref{sec:page-dist}) shows that citation matches do not reach zero at Pages~15--16; the long tail continues with a smooth decay curve. Extending to Rank~300 or beyond would likely recover additional matches and further narrow the ``truly invisible'' set (see Section~\ref{sec:fw-deeper-crawling}).

In the full scrape (Table~\ref{tab:bing-full}), Page~1 returned 7 tightly relevant video translation tools. In the truncated scrape (Table~\ref{tab:bing-truncated}), the same query returned only \texttt{zeemo.ai} and \texttt{wayin.ai} on Page~1; the remaining 5 results (ranks 3--7, bolded in Table~\ref{tab:bing-full}) were lost entirely; they did not resurface on Page~2 or at any subsequent depth, even when scraping to Rank~200.

Page~2 exhibited two notable patterns. First, a sharp relevance drop: the truncated run's Page~2 included \texttt{a2e.ai} (uncensored AI videos) and \texttt{dreamfaceapp.com} (image generation), off-topic results that would never appear on a well-curated Page~1. The full run's Page~2 similarly included \texttt{pdftranslate.ai} (PDF translation) and \texttt{lipsync.video} (lip-sync tool), tangentially related at best. Second, both Page~2 results shared a similar character despite their Page~1 results differing substantially: \texttt{notegpt.io} and \texttt{maestra.ai} appeared on Page~2 in both runs. This suggests that Bing's Page~2 starts from a fixed offset regardless of how many organic results Page~1 actually displayed. From Page~3 onward, continuity resumed with a gradual decay. Our citation-overlap data corroborates this pattern: Page~1 concentrates the bulk of matches, Page~2 shows a conspicuous dip, and Pages~3+ settle into a gradual decay (Section~\ref{sec:page-dist}).

This instability has two consequences for our overlap measurements. First, it introduces a conservative bias: if our scrape captured a truncated Page~1, we may have missed high-ranking results that ChatGPT's backend integration almost certainly had access to, causing us to classify some citations as ``invisible'' when they were in fact present in the index. Second, it is why we needed to scrape to Rank~200, not because ChatGPT is truly ``deep hunting'' at those ranks, but to compensate for UI-layer instability and recover matches that a stable API would have returned in the Top~10--30.

We strongly suspect that ChatGPT does not receive the same noisy, truncated pagination that Bing's web UI serves to human users. Bing likely provides its index to ChatGPT via a backend integration that returns a clean, stable ranked list without ads, carousels, or pagination artifacts. Our Bing-UI-scraped baseline is therefore a degraded proxy for what ChatGPT actually sees, further supporting the interpretation that our overlap figures are conservative lower bounds. This instability was not observed in our Google SERP data collected via SerpApi, which returned consistent, stable organic rankings across paginated requests, an asymmetry worth noting for researchers attempting to replicate grounding studies.

\section{Analysis Applications}
\label{sec:analysis-applications}

We built two separate interactive tools for qualitative inspection and aggregate analysis. The \textbf{ChatGPT Analysis Viewer} provides per-query/run comparison of ChatGPT responses against Bing SERP results (Top~200), highlighting cited, additional, and invisible links with overlap status. It includes an aggregate dashboard and enabled the manual spot-checking that revealed the Bing pagination instability documented in Section~\ref{sec:bing-pagination-instability}. The \textbf{Gemini Grounding Analyzer} provides the equivalent for Gemini, visualizing the grounding pipeline by comparing grounding chunks against grounding supports against the Google SERP control, with per-query-index overlap distributions and aggregate grounding dashboards.

\section{Content DNA Enrichment (LLM-as-a-Labeler)}
\label{sec:content-dna}

To quantify selection effects (what gets cited versus what was available), we needed to move beyond URLs and domains to a structured profile of each page's content characteristics.

\subsection{The Labeling Pipeline}
\label{sec:labeling-pipeline}

We developed an automated enrichment pipeline using GPT-5-mini and Gemini~2.5~Flash as structured labelers. The pipeline operates in three stages. First, raw HTML was fetched for each URL and converted to clean markdown/text. Second, the LLM was prompted to evaluate each page against a structured schema covering page type (\texttt{listicle}, \texttt{product\_page}, \texttt{documentation}, \texttt{forum\_ugc}), content format (\texttt{best\_of\_list}, \texttt{landing\_page}, \texttt{comparison\_matrix}), and structural features (\texttt{has\_tables}, \texttt{has\_numbered\_lists}, \texttt{has\_pros\_cons}). The schema also captured tone and promotional intensity scores, but these showed no discriminative power in downstream analysis (tone distribution was uniformly $\sim$70\% promotional across all systems, a natural consequence of the product-recommendation prompt set) and are omitted from the findings. Third, a subset of labels was manually audited to ensure the labeler correctly distinguished between vendor-owned landing pages and independent editorial listicles.

\subsection{Enrichment Logic and Static Overrides}
\label{sec:enrichment-logic}

The labeling pipeline uses a hybrid approach. General web pages, blogs, and niche product sites were labeled by GPT-5-mini. However, high-volume domains with fixed, well-understood structures were assigned static ``pre-made'' labels to save API quota and ensure consistency: \texttt{reddit.com} was labeled as \texttt{forum\_ugc}, \texttt{en.wikipedia.org} as \texttt{reference}, \texttt{arxiv.org} as \texttt{academic\_paper}, and app stores (\texttt{apps.apple.com}, \texttt{play.google.com}) as \texttt{app\_store\_listing}. Many of the top ``invisible'' domains (Section~\ref{sec:top-invisible-domains}) were handled via these static overrides because their structure does not require per-page LLM analysis.

A consistent skip list (\texttt{wikipedia.org}, \texttt{reddit.com}, \texttt{arxiv.org}, \texttt{github.com}, \texttt{youtube.com}, app stores, social media platforms, and first-party support/docs sites) was applied across all enrichment runs. These domains have fixed, well-understood structures (a Wikipedia article is always \texttt{type=reference}, a Reddit thread is always \texttt{type=forum\_ugc}), and their content is unlikely to contain the structural features (comparison tables, numbered lists, pros/cons blocks) that drive our drift analysis. They were therefore assigned heuristic labels with conservative defaults rather than full LLM enrichment.

\textbf{Consequence for drift analysis:} Because these skipped domains receive zeroed-out structural scores (no tables, no numbered lists, no pros/cons), including them in feature-level drift comparisons would create artificial signal. The selection drift analysis in Section~3.5 therefore focuses on \textbf{product pages and listicles}, the two dominant types where full LLM enrichment was performed and where structural features are meaningfully variable. This scoping avoids comparing LLM-enriched pages against heuristically-labeled ones, which would conflate labeling method differences with actual content differences.

\subsection{Labeler Fidelity (cross-model agreement)}
\label{sec:labeler-fidelity}

To test whether Content DNA is model-dependent, we ran a direct agreement audit between \textbf{Gemini 2.5 Flash} and \textbf{GPT-5-mini} on \textbf{2,660 overlapping URLs} (\texttt{docs/inter\_model\_fidelity\_report.md}).

\begin{itemize}
    \item \textbf{Structural fields (agreement)}: \texttt{has\_pros\_cons} \textbf{94.6\%}, \texttt{has\_sources\_or\_citations} \textbf{93.8\%}, \texttt{has\_clear\_authorship} \textbf{93.3\%}, \texttt{has\_tables} \textbf{92.9\%}, \texttt{has\_numbered\_lists} \textbf{91.1\%}
    \item \textbf{Categorical fields (agreement)}: \texttt{content\_format} \textbf{92.1\%}, \texttt{type} \textbf{87.7\%}, \texttt{tone} \textbf{77.7\%}
    \item \textbf{Score consistency (correlation)}: \texttt{freshness\_cue\_strength} \textbf{$r = 0.841$} (strong trend agreement, different absolute thresholds)
\end{itemize}

A parallel cross-model validation was performed on the listicle semantic fidelity judge (Section~\ref{sec:semantic-fidelity}), where all 1{,}116 claims were judged by both models. Agreement rates (93--100\% on structural fields, 93.9\% within $\pm$1 on fidelity scores) are consistent with the DNA labeler results above.

\subsection{Research Questions for Selection Analysis}
\label{sec:selection-research-questions}

The enrichment data enables three lines of analysis. First, we compare the structural DNA of cited versus additional links to identify which content features predict inline citation versus supplementary attachment. Second, we track cross-run citation consistency: whether URLs demoted to ``additional'' in one run are promoted to ``cited'' in a different run of the same prompt, quantifying the stochasticity of the citation boundary (Section~\ref{sec:flip-flop}). Third, we compare the DNA of Bing Page~1 or Google Top 10 links that ChatGPT ignored against those it cited, testing whether ignored links exhibit lower structural complexity (Section~\ref{sec:cited-vs-serp}).

\section{Use of AI Tools in This Research}
\label{sec:ai-tools-disclosure}

This thesis made extensive use of large language models as research tools at every stage of the work. We disclose this both for transparency and because we believe it reflects the reality of how empirical research involving LLMs is increasingly conducted.

\textbf{Data enrichment and judging.} The Content DNA labeling pipeline (Section~\ref{sec:labeling-pipeline}) used \textbf{GPT-5-mini} and \textbf{Gemini 2.5 Flash} as structured labelers to classify $\sim$6{,}000 URLs. The semantic fidelity judge (Section~\ref{sec:semantic-fidelity}) used the same two models to evaluate 1{,}116 listicle product claims. Cross-model agreement was validated in both cases (91--100\% on structural fields), and all flagged attribution failures were manually verified.

\textbf{Analysis scripting.} Many of the analysis scripts (Python, Node.js) were written with AI assistance using multiple models across two IDE integrations: \textbf{Gemini 3.0 Flash} (Google) was the primary model used via Cursor, with \textbf{GPT-5.2} and \textbf{GPT-5.2 Codex} (OpenAI) and \textbf{Claude Opus 4.5} (Anthropic) used occasionally via Cursor as well. Later-stage analysis and writing shifted to \textbf{Claude Opus 4.5/4.6} via Claude Code. The author specified the analysis logic, reviewed all outputs, and iteratively refined both the code and the interpretation of results through extended dialogue with the models.

\textbf{Writing and editing.} Drafts of thesis prose, tables, and \LaTeX{} formatting were developed in collaboration with Claude Opus 4.5/4.6 via Claude Code. Later-stage proofreading, formatting, and literature search were also assisted by \textbf{OpenAI Prism}, a \LaTeX-native workspace with integrated GPT-5.2. The workflow was dialogic: the author provided the arguments, data, and framing decisions; the models produced draft text; the author reviewed, challenged, and revised. Every finding, interpretation, and number in this thesis was verified by the author against the underlying data. The intellectual contribution (the research questions, the experimental design, the instrumentation approach, and the analytical arguments) is the author's own.

We note a reflexive dimension to this disclosure: a thesis that studies how LLMs ground their outputs in web sources was itself produced with LLMs as writing and analysis tools, subject to the same grounding and fidelity questions we investigate. We consider this appropriate rather than paradoxical; the tools we study are the tools of our era, and using them transparently is preferable to understating their role.
