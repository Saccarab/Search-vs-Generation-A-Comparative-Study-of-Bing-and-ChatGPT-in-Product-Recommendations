\chapter{Findings \& Analysis}
\label{ch:findings}

This chapter traces the full retrieval-to-citation pipeline, organized to mirror the stages through which a user's prompt becomes a set of product recommendations. We begin with the retrieval strategy itself---how models reshape a single prompt into multiple search queries (Section~\ref{sec:fanout})---and then follow the results through the pipeline: how citations are distributed across SERP pages (Section~\ref{sec:position-bias}), what fraction of citations exist in conventional search indices and how provider strategy differs across deployment tiers (Section~\ref{sec:citation-overlap}), how rank position within pages shapes citation likelihood (Section~\ref{sec:gemini-google-rank}), what the ``invisible'' remainder looks like and how citation status fluctuates across runs (Section~\ref{sec:invisible-links-section}), how the structural characteristics of cited sources differ from the available pool (Sections~\ref{sec:content-dna}--\ref{sec:selection-drift}), and finally how the model extracts and reproduces individual products from within cited listicles (Section~\ref{sec:listicle-bias}).

%-----------------------------------------------------------------------
\section{Retrieval Strategy \& Fan-Out Analysis}
\label{sec:fanout}

This section examines the retrieval phase: how models reshape a single user prompt into multiple search queries before any citation decision occurs. The instrumentation and methodology underpinning these observations are defined in Sections~2.3.4, 2.7.1, and~2.7.2.

\subsubsection{The Three-Layer Architecture (as observed)}
\label{sec:three-layer}

Our network instrumentation reveals a three-layer pipeline, not a monolithic model. The high-level flow as observed in the event stream:
\begin{enumerate}
    \item \textbf{User prompt received.}
    \item \textbf{Search decision (Layer~1 --- Sonic Classifier):} a three-class classifier (\texttt{sonic\_classifier\_5p2\_3cls\_ev3}) fires once per turn and outputs \texttt{simple\_search\_prob}, \texttt{complex\_search\_prob}, and \texttt{no\_search\_prob} (summing to 1.0). These are evaluated against thresholds in priority order (\texttt{no\_search} $\rightarrow$ \texttt{complex} $\rightarrow$ \texttt{simple}). If \texttt{no\_search\_prob} $\geq 0.175$, the classifier signals suppression; otherwise it signals search (though external mechanisms can still override this decision---see below). The classifier's probability output is deterministic: the same prompt on the same account tier produces byte-identical probabilities across runs. However, whether search ultimately fires also depends on external mechanisms that can override the classifier's decision (see below), which is why some prompts show mixed search behaviour across runs despite stable classifier output.
    \item \textbf{Fan-out query generation + retrieval (Layer~2 --- Sonicberry Orchestrator):} an orchestrator (\texttt{alpha.sonic\_thinky\_v1\_paid}) manages the \texttt{web.run} tool-call loop. Each \texttt{web.run} call dispatches exactly 2 reformulated queries. Results return as \texttt{search\_result\_groups}.
    \item \textbf{Re-search decision (Layer~3 --- Generation Model):} the generation model (\texttt{gpt-5-2}) evaluates the retrieved pool and may call \texttt{web.run} again (incrementing \texttt{search\_turns\_count}). This creates an agentic re-search loop --- 94\% of runs complete in 1 turn (2 queries), 2.5\% require 2 turns (4 queries), 0.2\% require 3 turns (6 queries). Unlike the classifier, this decision is non-deterministic: the same input can produce different turn counts across runs.
    \item \textbf{Selection:} the model promotes some sources to be cited inline, and may also attach extra sources as ``additional.''
    \item \textbf{Generation:} answer text is streamed with citation tokens (e.g., \texttt{citeturn0search0}) that are merged into the final response.
\end{enumerate}

\subsection{ChatGPT Search Trigger Behavior}
\label{sec:search-trigger}

A prerequisite to any fan-out analysis is determining when ChatGPT triggers web search at all. The Sonic Classifier, a three-class model that fires once per conversation turn, governs this decision.

\begin{itemize}
    \item \textbf{Overall search rate:} \textbf{89.0\%} of 474 runs triggered web search (422/474). Business: \textbf{91.1\%}, Personal: \textbf{86.9\%} --- a 4.2~pp gap.
    \item \textbf{Classifier behavior:} The Sonic Classifier output a median \texttt{simple\_search\_prob} of \textbf{96.8\%} for product-recommendation prompts. Neither the \texttt{complex\_search\_threshold} (0.4) nor the \texttt{no\_search\_threshold} (0.175) was ever crossed --- all runs fell into ``simple search'' territory. The closest miss: P016 business at \texttt{no\_search\_prob} = 0.1737 (missed the 17.5\% gate by 0.0013).
    \item \textbf{External suppression:} The 52 no-search runs were \textbf{not} caused by the classifier's probability output:
    \begin{itemize}
        \item 39 runs had \textbf{null classification} (classifier never executed; raw network response files were empty)
        \item 13 runs had the classifier \textbf{overridden} despite \texttt{simple\_search\_prob} as high as 99.7\% --- the exact suppression mechanism is not visible in the payload, but plausible candidates include server-side A/B gates, tool routing logic (\texttt{passthrough\_tool\_calls}), or session-level factors. These overrides occurred predominantly on Personal accounts (11 of 13)
    \end{itemize}
    \item \textbf{Prompt-level consistency:} 61/79 prompts (77.2\%) always triggered search across all 6 runs; 6 prompts (7.6\%) never triggered search; 12 prompts (15.2\%) showed mixed behavior --- P016 had a perfect 50/50 split.
    \item \textbf{Citation impact:} Search-triggered runs averaged \textbf{9.94 citations/run} vs \textbf{2.62} for no-search runs (\textasciitilde4x). Business no-search runs averaged just 1.10 citations; Personal no-search runs managed 3.65, suggesting Personal more readily generates citation-like references from parametric memory. For context, \textcite{punturo2026citationsources} report $\sim$4 unique citations per search-triggered turn across 730K general-purpose conversations---our 2.5$\times$ higher rate reflects the comprehensive sourcing that product-finding prompts demand compared to average ChatGPT usage, which includes many non-search intents (coding, creative writing, casual conversation).
    \item \textbf{Ghost citations:} 7 runs (all Personal) produced citation-formatted markers with \textbf{zero backing URLs}---the model generated text that looks like a sourced reference (e.g., bracketed numbers or inline links) but with no actual URL in the payload behind them, amounting to hallucinated citation syntax.
    \item \textbf{Parametric URL recall:} A further 5 no-search runs (all Personal) produced \textbf{fully sourced citations without web search}---up to 14 real URLs per run, recalled entirely from the model's training data rather than live retrieval. This demonstrates that the generation model can surface specific URLs from parametric memory when the search pathway is suppressed.
\end{itemize}

\paragraph{Sonic Classifier configuration (observed across all 474 runs):}
\begin{itemize}
    \item \textbf{Classifier:} \texttt{sonic\_classifier\_5p2\_3cls\_ev3} (model: \texttt{snc-pg-sw-3cls-ev3}, snapshot: \texttt{wli-searchdb-model5-2025-09-23-20-17}). This version was identical across both Business and Personal tiers---same model, same snapshot, same thresholds---and remained constant throughout our data collection window (January 2026). The version identifier is significant: independent observations document a structurally different classifier (\texttt{sonic\_force\_pg\_switcher}) on the free tier (see note below), indicating that classifier behavior can change substantially between versions and plan tiers.
    \item \textbf{3-class output:} \texttt{simple\_search\_prob} + \texttt{complex\_search\_prob} + \texttt{no\_search\_prob} = 1.0
    \item \textbf{Thresholds (evaluated in order):}
    \begin{enumerate}
        \item \texttt{no\_search\_threshold} = 0.175
        \item \texttt{complex\_search\_threshold} = 0.4
        \item \texttt{simple\_search\_threshold} = 0 (catch-all)
    \end{enumerate}
    \item \textbf{First-turn override:} \texttt{force\_search\_first\_turn\_threshold} = 0.00001 (near-zero, almost always forces search on first message)
    \item \textbf{Business vs.\ Personal config divergence:} Both tiers use the same classifier model and thresholds, but differ in peripheral settings: Business has \texttt{prefetch\_threshold: null} + \texttt{passthrough\_tool\_calls: true}; Personal has \texttt{prefetch\_threshold: 0.55} + no passthrough tools
\end{itemize}

\paragraph{The search-default paradigm shift.} The most architecturally significant finding from our classifier analysis is the inversion of the search decision's burden of proof. Earlier versions of the classifier, documented by \textcite{resoneo2025chatgpt} and \textcite{williamscook2025sonic}, used a single \texttt{search\_prob} that had to exceed a threshold (65\%) before web search would fire---making parametric inference the default and search opt-in. The version we observe on paid tiers inverts this: search is the \emph{default}, and is suppressed only if \texttt{no\_search\_prob} $\geq 0.175$. The question the classifier answers is no longer ``should I search?'' but ``should I \emph{not} search?''---and with a catch-all \texttt{simple\_search\_threshold} of~0, any prompt that fails to clear the suppression gate will trigger retrieval. For product-recommendation queries, this means web grounding is near-guaranteed on paid tiers.

\paragraph{Free-tier vs.\ paid-tier divergence.} The Resoneo and Williams-Cook observations appear to describe the free-tier classifier (\texttt{sonic\_force\_pg\_switcher}), which retains the older opt-in architecture with a single probability and a higher activation threshold. This architectural divergence---opt-in search on the free tier versus opt-out search on paid tiers---is consistent with practitioner observations that paid plans trigger grounding more aggressively, and means our findings on search trigger rates, fan-out behavior, and citation selection apply specifically to paid ChatGPT deployments.

\paragraph{Scope caveat:} Because our 79 prompts were deliberately designed to elicit product recommendations requiring web data, the classifier overwhelmingly routed them to search---no run ever crossed the \texttt{no\_search\_threshold} or the \texttt{complex\_search\_threshold}. The thresholds and cascade logic described above are extracted from the classifier's configuration payload, not from empirical observation of suppression events. The 52 no-search runs in our dataset resulted from external mechanisms (null classification or server-side overrides), not from the classifier's probability output exceeding the configured gate. A fuller discussion of this limitation and its implications is in Section~\ref{sec:lim-search-trigger}.

\subsection{Freshness Steering}
\label{sec:freshness-steering}

\begin{itemize}
    \item \textbf{Gemini: Explicit Freshness Obsession:} \textbf{96.7\%} of Gemini runs (297/307 with valid grounding metadata) explicitly inject a year (2025 or 2026) into their fan-out queries. Of these, \textbf{74.3\%} (228/307) place the year signal in the very first query (Index 0), while a further \textbf{22.5\%} (69/307) include it only in later queries. Just \textbf{3.3\%} (10/307) of runs contained no year signal at all. This drives Gemini's aggressive ``Listicle Uptake'' --- by explicitly searching for ``Best [Product] 2025,'' the model forces the retrieval of time-stamped listicles, which then dominate its grounding.
    \item \textbf{GPT: Implicit Recency Reliance:} Only \textbf{5.1\%} of GPT runs use explicit year signals in their fan-out queries. GPT relies almost entirely on the search index's (Bing's) internal recency ranking, leading to a more diverse (though still listicle-leaning) grounding pool.
    \item \textbf{GPT's Multi-Turn Re-Search:} In a small minority of runs (\textasciitilde3\%), the generation model issued additional \texttt{web.run} calls after evaluating initial results. This is distinct from the classifier's complex-search pathway (which was never triggered); multi-turn re-search is an emergent Layer~3 decision. Gemini exhibits multi-query fan-out far more frequently by design. Empirical details are in Section~\ref{sec:multi-turn}.
\end{itemize}

\paragraph{Query drift:} Across multiple runs of the same prompt, the fan-out query set can vary. This drift is a primary driver of stochastic retrieval---different fan-out sets lead to different retrieved sources and therefore different citations/recommendations.

\subsection{Cross-Language Fan-Out \& Localization Bias}
\label{sec:localization-bias}

ChatGPT injects cross-language queries into its fan-out---driven by prompt language, geographic context, and IP/locale signals---meaning a user searching in one language will have part of their retrieval routed through a different language's search index. This operates in both directions: foreign-language prompts receive English fan-outs, and English prompts can receive foreign-language fan-outs based on IP geolocation. Gemini, which we accessed via the Vertex~AI API without IP or locale signals, exhibits a narrower and unidirectional pattern: for foreign-language prompts it consistently anchors the first fan-out query in English, but we never observed the reverse---English prompts never received foreign-language fan-outs (Section~\ref{sec:gemini-english-anchor}). In both systems, cross-language routing has implications for which publishers gain or lose visibility.

Our dataset consists of 72 English prompts and 7 foreign-language prompts (1~French, 1~Chinese, 2~Turkish, 1~German, 1~Italian, 1~Spanish). All 7 foreign-language prompts originated from Ahrefs keyword clusters; the Profound-sourced prompts were exclusively English.

We distinguish two forms of localization. \textbf{Explicit localization} occurs when the query targets an inherently local category---even without a geographic qualifier, a query like ``best bakery'' triggers location-injected fan-out queries (e.g., ``best bakery near Munich Germany''). This primarily applies to local-commerce queries and is not a factor in our SaaS/software dataset. \textbf{Implicit localization} occurs when the search engine uses the user's IP, browser language, or search history to localize results for a general query. In our fan-out data, implicit localization manifests as one of the two fan-out queries being rewritten into the prompt's local language. For example, when issuing an English prompt from Munich, Germany, we observed one query in English (\texttt{"free website or program to translate video and add subtitles"}) and a parallel query in German (\texttt{"kostenlos video \"ubersetzen und Untertitel automatisch hinzuf\"ugen\ldots"})---routing half the retrieval into the German-language index despite an English user prompt.

\subsubsection{GPT: Cross-Language Fan-Out Taxonomy}

Cross-language fan-out signals were observed in \textbf{13.1\%} of GPT runs (62/474), distributed across three distinct patterns:

\begin{enumerate}
    \item \textbf{Case~1 --- Foreign prompt $\rightarrow$ English fan-out (6.3\%, 30 runs):} The user searches in a non-English language; GPT generates one fan-out query in English alongside one in the user's language. The English query typically targets global review sites and English-language listicles, pulling the grounding pool toward anglophone sources.

    \item \textbf{Case~2 --- English prompt + foreign context $\rightarrow$ local-language fan-out (1.9\%, 9 runs):} The user searches in English but the prompt references an inherently local category (e.g., ``best pizza in Istanbul,'' ``local translation services in Berlin''). GPT responds by generating a locale-aware fan-out query in the relevant local language (Turkish, German), alongside the English query.

    \item \textbf{Case~3 --- English prompt, no foreign context $\rightarrow$ foreign-language fan-out (4.9\%, 23 runs):} The user searches in English with no geographic or cultural markers in the prompt, yet GPT generates a non-English fan-out query. These ``untriggered'' localizations are consistent with OpenAI's documented behaviour: ChatGPT ``collects general location information based on your IP address and may share that general location with third-party search providers to improve the accuracy of your results'' \parencite{openai2024searchhelp}. The model infers the user's location and proactively diversifies retrieval into the local language even when the user gave no such signal.
\end{enumerate}

Cases~2 and~3 vary in cross-run consistency: some prompts exhibit the behavior on every run (e.g., P018), while others do so only sporadically (e.g., P048 in 2 of 3 runs). Cases~2 and~3 are GPT-only observations; Gemini was accessed via the Vertex~AI API without IP-based locale signals, so these patterns could not be tested (Section~\ref{sec:gemini-instrumentation-differences}).

In all three cases, the fan-out query pair is split: one query in language~A, one in language~B. This means the retrieval pool is drawn from two separate language indexes of the search engine.

\subsubsection{External Validation at Scale}

Our Case~1 finding is corroborated at scale by \textcite{rudzki2026english}, who analyzed over 10~million prompts and 20~million query fan-outs from Peec~AI's production monitoring data (controlling for location-language matching). They report that \textbf{78\%} of non-English ChatGPT sessions include at least one English-language sub-search, and \textbf{43\%} of all fan-out queries for non-English prompts target the English web. Our Case~1 rate (6.3\%) represents a lower bound because our dataset is predominantly English-language prompts; the Peec~AI data confirms that when users \emph{do} search in foreign languages, the English fan-out is near-universal.

\textbf{Scope of corroboration:} Rudzki's analysis exclusively covers Case~1 (foreign prompt $\rightarrow$ English fan-out). \textbf{Cases~2 and~3---where English-language prompts receive foreign-language fan-outs---are unique to our study} and represent a novel empirical contribution. The reverse direction of the bias (English users losing visibility to IP/geolocation-driven localized retrieval) has not been previously documented.

\subsubsection{Gemini: The ``English Anchor'' Effect}
\label{sec:gemini-english-anchor}

Because our Gemini data was collected through the Vertex~AI API (which does not carry IP or locale signals), we cannot test whether Gemini exhibits the same IP/locale-driven localization as GPT. This remains a limitation (see Section~2.4.2). However, we observe a distinct pattern:

\begin{itemize}
    \item Even for foreign-language prompts, Gemini \textbf{always} reserves the first grounding-support query slot (Index~0) for an English translation of the prompt.
    \item Due to the \textbf{First-Query Bias} (Section~\ref{sec:per-query-citation}), English-language search results dominate the final response.
    \item In 100\% of our localized Gemini runs, the cited sources were primarily global/English SaaS platforms and tech publications (e.g., \texttt{pcmag.com}, \texttt{techradar.com}), creating a ``Global Information Bubble'' even for non-English users.
\end{itemize}

\subsubsection{Publisher \& GEO Implications}

\begin{enumerate}
    \item \textbf{Non-English publishers lose visibility (Case~1):} When foreign-language queries get an English fan-out (78\% of the time per Peec~AI), English-language sources enter the grounding pool and compete directly with local-language sources. Given LLMs' structural preference for well-formatted English listicles (see Section~\ref{sec:selection-drift}), local publishers face a systematic disadvantage.
    \item \textbf{English-only publishers lose visibility (Cases~2--3):} Conversely, when English-speaking users get localized fan-outs (6.8\% of our runs), publishers without localized pages are invisible to that retrieval path. Even if a publisher ranks well in English SERPs, IP-driven localization can route part of the LLM's retrieval away from their content.
    \item \textbf{The language of optimization matters:} Traditional SEO focuses on ranking in the user's query language. GEO must account for the fact that the LLM may search in a \emph{different} language than the user typed.
\end{enumerate}

\subsection{Invisible Links --- The Visibility Gap}
\label{sec:invisible-links}

We use \textbf{Visibility Gap} as the empirical gap between what is \textbf{cited} and what is visible in conventional SERP UX. The methodological pivot (Top-30 $\rightarrow$ Deep Hunt Rank-200) is defined once in Section~2.2; here we report the \textbf{residual unmatched} set and what it looks like. This analysis focuses on ChatGPT, where the invisible-link question is most consequential: ChatGPT dominates LLM search traffic (Section~\ref{sec:commercial-catalyst}), and the relationship between its citations and the Bing index is not self-evident. Gemini grounds on Google's own index, making an invisible-link analysis less revealing---the interesting question for Gemini is not \emph{whether} it draws from Google, but \emph{how} it selects within that index, which we address in the selection drift and fidelity analyses.

\begin{itemize}
    \item \textbf{What is being compared}: \textbf{cited URLs} vs \textbf{presence/absence} in the \textit{per-run} SERP snapshot (and/or Bing Deep Hunt $\leq$200).
    \item \textbf{Output}: \textbf{matched} vs \textbf{invisible} (unmatched).
    \item \textbf{Invisible rate (headline)}: use the \textbf{``Invisible (Missing)''} row in Section~\ref{sec:global-overlap} as the canonical rate.
    \item \textbf{Long tail context} (how deep ``matched'' links are): see Section~\ref{sec:page-dist} (Bing Pages 1--16).
\end{itemize}

\subsubsection{Scraping Limitations that Inflate the Invisible Count}
\label{sec:invisible-conservative}

Our reported invisible rates (16.3\% Business, 19.4\% Personal) are \textbf{upper bounds} on truly index-absent citations. Two systematic factors inflate the invisible count:

\begin{enumerate}
    \item \textbf{The Rank 200 ceiling}: Our Bing scrape stops at Rank 200, but the page-level match histogram (Section~\ref{sec:page-dist}) shows no convergence---matches are still accumulating at Pages 15--16 with a smooth decay curve that does not reach zero. Scraping to Rank 300 or 400 would almost certainly recover additional matches, shrinking the invisible set. The ``invisible'' label for these URLs does not mean they are absent from Bing's index---only that they fell beyond our scrape depth.

    \item \textbf{Bing Page 1 truncation}: As documented in Section~2.2.1, nearly half of our Bing scrapes had 5 or fewer organic results on Page~1 due to UI-level pagination instability. Results that would normally rank at positions 3--7 can be dropped entirely from a truncated scrape---they do not simply shift to Page~2. This is especially consequential because Page~1 is where we observe the highest match rates (Section~\ref{sec:page-dist})---so every result missed due to Page~1 truncation is statistically more likely to be a citation match than a result missed deeper in the index. These ``missing middle'' results are almost certainly available to ChatGPT through its backend API integration with Bing, which likely returns a clean, stable ranked list without the consumer UI's truncation artifacts.
\end{enumerate}

Both factors disproportionately affect \textbf{niche SaaS and product domains}---the very category our prompt set targets. These domains are likely present in the Bing index but fell beyond our scrape depth or were lost to Page~1 truncation. Using our Content DNA page-type labels (Section~\ref{sec:content-dna}), we identify and \textbf{exclude} URLs classified as \texttt{product\_page} from the invisible domain tables below. This filtering is modest---removing 31 entries (4.0\%) for Business and 113 entries (6.7\%) for Personal---so the resulting tables are not substantially altered, but the excluded entries are precisely the category most vulnerable to the two scraping artifacts above.

\subsection{Rejected Links --- The Search Pool Remainder}
\label{sec:rejected}

They never appear in the user-facing response.

\paragraph{How we identified rejected links:} Our ingestion pipeline parses each run's raw network response, extracts all URLs from the \texttt{search\_result\_groups\_json} field, then subtracts any URL already classified as cited or additional. The remainder is classified as ``rejected.''

\paragraph{Interpretation --- what role do rejected links play?}

\paragraph{Rejected--to--promoted promotion rate.}
The boundary between rejected and cited/additional is itself stochastic. Comparing across runs of the same prompt, \textbf{7.9\%} of Business rejected URL--prompt pairs and \textbf{9.8\%} of Personal pairs appear as cited or additional in at least one other run. This means the three-tier classification (cited, additional, rejected) reflects a \textbf{continuum of stochastic thresholds} rather than categorical distinctions: the cited$\leftrightarrow$additional boundary flips in $\sim$20\% of cases (Section~\ref{sec:flip-flop}), and the rejected$\leftrightarrow$cited/additional boundary flips in $\sim$8--10\%.

\section{Selection Drift (Enrichment-Based)}
\label{sec:selection-drift}

With the DNA profile established in Section~\ref{sec:content-dna}, we now measure how each model's selection systematically diverges from the available pool along enriched feature dimensions.

\textbf{Methodology---per-run, SERP-constrained Welch's t-test:} For each run, every SERP URL (filtered by content type) is classified as either \textbf{Cited} or \textbf{Not-Cited} in that run. A cited URL only counts if it also appears in the SERP for that run, ensuring both groups are drawn from the same retrieval pool. Zero overlap between groups. A URL may appear in multiple runs; each is an independent selection event. We test eight binary Content DNA features using Welch's two-sample t-test. \texttt{freshness\_cue\_strength} is binarized at $\geq$3 (``strong freshness cues''). A per-unique-URL robustness check (deduplicating across runs) produces the same direction of drift for every significant feature, confirming that [saying confirm again sdoesnt make sense use more humble words] the results are not driven by repeated counting.

\textbf{GPT data:} SERP from Bing Page~1 (business + personal) and Google Top-10 (personal only).

\textbf{Gemini data:} SERP from Google Top-10 (fan-out queries via SerpApi). Cited URLs reconstructed per-run from raw Gemini responses via \texttt{master\_bundle.json} (Vertex grounding chunks resolved to real URLs; 2{,}278 mappings, 100\% coverage).

\textbf{Two-stage decomposition (GPT only):}
\begin{enumerate}
\item \textbf{Cited vs Not-Cited from SERP:} For each run, SERP URLs are split into Cited vs Not-Cited. This captures the full end-to-end selection effect.
\item \textbf{Cited vs Additional:} Both groups were surfaced by ChatGPT. Cited = appeared in response text. Additional = supplementary sources. This isolates the final citation preference from an already-filtered pool. Gemini lacks an ``additional'' citation category, so this test is GPT-only.
\end{enumerate}

\subsection{Interpretation}
\label{sec:drift-interpretation}

\subsubsection{Two-Stage Pipeline (GPT)}

The comparison between Stage~1 and Stage~2 reveals \emph{where} structural selection occurs:

\begin{itemize}
\item \textbf{Stage 1 (Cited vs Additional):} Modest drifts. Business listicles: 1 significant feature. Personal listicles: 3. The Additional pool is structurally similar to the Cited pool because both have already passed the model's retrieval filter.
\item \textbf{Stage 2 (Cited vs Not-Cited from SERP):} Much larger drifts. Business listicles: Tables $+$11.4pp ($p<0.01$), Numbered Lists $+$10.3pp ($p<0.001$). Personal listicles vs Google: 5/8 features significant, Tables reaching $+$19.7pp.
\end{itemize}

This decomposition shows that \textbf{most structural selection happens at the retrieval/surfacing stage, not the citation stage.} ChatGPT's retrieval pipeline already over-selects for structured, scannable content from the SERP. The subsequent citation-stage filter refines this with smaller effect sizes.

\subsubsection{Cross-Model Comparison}

With per-run, SERP-constrained methodology applied to both models, \textbf{Gemini also shows significant structural selection}. Gemini listicles show 4 of 8 features significant, with Vendor Owned $+$8.6pp ($p<0.001$), Tables $+$7.8pp ($p<0.01$), and Numbered Lists $+$7.1pp ($p<0.01$).

\textbf{Shared patterns across both models (listicles):}
\begin{itemize}
\item \textbf{Over-selected:} Tables, numbered lists, bullet points, vendor-owned sources
\item \textbf{Directionally under-selected:} Sources/citations show negative drift for most conditions, reaching significance for GPT Personal vs Bing ($-$11.1pp, $p<0.01$) and Gemini product pages ($-$3.6pp, $p<0.001$)
\end{itemize}

\textbf{Key differences:}
\begin{itemize}
\item \textbf{Clear Authorship:} ChatGPT shows negative authorship drift across conditions ($-$1.8 to $-$11.9\,pp, not significant under SERP constraint), while Gemini \emph{over-selects} pages with clear bylines ($+$5.9pp, $p<0.05$). The directional divergence persists, though the SERP constraint attenuates statistical significance on the GPT side.
\item \textbf{Freshness:} ChatGPT shows strong freshness preference (up to $+$16.6pp for Personal vs Bing, $+$9.4pp vs Google, both $p<0.001$), while Gemini shows no freshness drift---likely because 96.7\% of Gemini's fan-out queries already inject year tokens, pre-filtering the SERP for freshness.
\item \textbf{Effect sizes:} ChatGPT's largest drifts (Tables $+$19.7pp vs Google) exceed Gemini's (Vendor Owned $+$8.6pp, Tables $+$7.8pp), but Gemini's larger sample sizes ($N=468$ cited listicles vs $N=160$) give it more statistical power.
\end{itemize}

\textbf{Product pages} show flatter drift profiles across both models. Product pages are structurally homogeneous (high vendor-owned rates, low table/pros-cons rates), leaving less for either model to differentiate on. Gemini product pages show significant under-selection of pages with editorial sources/citations ($-$3.6pp, $p<0.001$); this signal is directionally present but not significant for GPT.

\section{Listicle Extraction \& Bias Analysis}
\label{sec:listicle-bias}

The preceding sections examined which \emph{pages} the model selects from the SERP. This section shifts the unit of analysis one level deeper: given that a listicle has been cited, which \emph{products within that listicle} does the model extract, and how faithfully does it reproduce their details? We investigate three phenomena: host-product exclusion, within-listicle position bias, and semantic fidelity of product claims.

\subsection{Scope: Solo-Cited Claims Only (Multi-Citation Filtering)}
\label{sec:solo-cited}

Listicle bias analysis requires attributing a product recommendation to a specific source. When a claim is backed by multiple citations (e.g., a listicle \textit{and} a product page), it becomes ambiguous which source drove the selection --- was the product picked because it appeared in the listicle, or because the model also had the vendor's own page? To avoid this attribution problem, the analyses in Sections~\ref{sec:self-promo}--\ref{sec:semantic-fidelity} are restricted to \textbf{solo-cited claims}: product recommendations backed by exactly one URL.

This filtering excludes a non-trivial share of claims. GPT produces 458 multi-cited claims out of 4,296 total claim occurrences (10.7\%), while Gemini produces 788 out of 2,287 (34.5\%). Among multi-cited claims involving at least one listicle, approximately 20\% are mixed listicle+product-page citations (GPT: 21.1\%, Gemini: 19.6\%). Gemini's higher multi-citation rate reflects its grounding architecture, which maps individual response segments to multiple \texttt{groundingChunks} --- producing richer but harder-to-attribute citation linkages.

The solo-cited filter is conservative: it discards cases where listicle influence may still be present but cannot be cleanly isolated. The trade-off is cleaner attribution at the cost of reduced sample size.

\subsection{Self-Promotion Bias \& Host Exclusion}

\subsection{Selection Order vs.\ Listicle Rank (The ``Re-Ranking'' Effect)}
\label{sec:reranking}

Do models preserve the internal ranking of a listicle when selecting products, or do they re-order items in their response? We measure this in two ways: \textit{rank alignment} (exact position match) and \textit{top-item skew} (over-selection from the top of the listicle).

\paragraph{Rank alignment.} We compare each product's position in the model's response (1st, 2nd, 3rd, \ldots) against its rank in the source listicle, restricting to cases where \texttt{listicle\_rank} is recoverable. Exact alignment is low: Gemini matches in 29.5\% of cases (108/366) and GPT in 27.9\% (166/596). Models therefore \textbf{re-rank} listicle items rather than preserving the source order.

\paragraph{Top-item skew.} Despite re-ranking, models strongly over-select items from the top of the listicle. The \#1 item in a listicle is selected at 1.7--2.5$\times$ the uniform baseline, and the top-5 items account for 76--81\% of all selections despite comprising roughly half the listicle on average. This mirrors the SERP-level position bias observed in Section~\ref{sec:position-bias}: just as models disproportionately cite Rank~1 in the SERP, they disproportionately extract the \#1 product from within a cited listicle. Position bias thus operates at two nested levels --- SERP rank and within-listicle rank.

A plausible mechanism for within-listicle position bias emerges from recent work on how LLMs process source content. \textcite{petrovic2025grounding} shows that Google's grounding infrastructure operates with a fixed ``content budget'' of approximately 2{,}000 words per query, with rank~\#1 sources receiving 28\% of the budget (531 words) versus 13\% for rank~\#5 (266 words); pages exceeding 3{,}000 words receive only 13\% coverage, meaning items listed further down a long listicle may never enter the grounding chunks sent to the model. \textcite{indig2026attention} reports a complementary finding for ChatGPT: 44.2\% of citations originate from the first 30\% of a source page's text (a ``ski ramp'' distribution, $p < 0.0001$ over 18{,}012 verified citations), with content in the final 30\% accounting for only 24.7\% of citations. Together, these findings suggest that the top-item skew we observe is not merely a learned preference but may reflect an architectural constraint: items positioned later in a listicle are less likely to be included in the content window the model actually processes.

\subsection{Semantic Fidelity: Reading Comprehension vs.\ Attribution}
\label{sec:semantic-fidelity}

The final question in the listicle pipeline is whether models accurately reproduce the details of products they extract. We decompose fidelity into two distinct phenomena:

\begin{enumerate}
    \item \textbf{Attribution accuracy}: Does the cited listicle actually contain the product the model claims it does?
    \item \textbf{Reading comprehension} (pure fidelity): When the product is present, how accurately does the model extract its details?
\end{enumerate}

We evaluate both using an LLM-as-judge approach, scoring fidelity on a 1--5 scale by comparing each product claim against the source listicle text. A single inline prompt performs all tasks per case: fidelity scoring, listicle presence verification, rank extraction, host-product detection, and roster-item classification. Cross-model validation (all 1{,}116 claims judged by both Gemini 2.5 Flash and GPT-5-mini) confirmed that structural fields agree at 93--100\% and fidelity scores agree within $\pm$1 in 93.9\% of 1{,}826 matched product pairs, consistent with the DNA labeler benchmark (Section~\ref{sec:labeler-fidelity}). Both models achieve near-perfect reading comprehension when the product is present in the source (4.71--4.81 out of 5.0). The primary failure mode is not misunderstanding but \textit{mis-attribution}: the model recommends a product and attaches a citation, but the cited listicle does not actually contain that product. All 44 cases initially flagged by the LLM judge were manually verified by inspecting the cited listicle page, the raw grounding metadata, and the model's response text. Of these, 12 proved to be false positives caused by the LLM judge missing products present under variant names, the GPT product-extraction pipeline misidentifying category descriptors as product names, or incomplete page fetches. The remaining 32 cases (27~Gemini, 5~GPT) are genuine attribution failures, yielding verified rates of 6.4\% for Gemini and 0.7\% for GPT. We note that this manual audit covers only the positive cases (items the judge flagged as failures); the negative cases --- where the judge confirmed the product was present --- were not independently re-checked, so the true failure rate may be marginally higher if the judge produced false negatives.

Critically, 15 of Gemini's 27 failures share a single root cause: \textit{table-attribution collapse}. When Gemini generates a summary comparison table, its grounding API assigns the entire table to a single source chunk, even though individual products in the table were correctly attributed to different sources earlier in the response. This is a systematic artefact of how Gemini's grounding infrastructure handles tabular output rather than a hallucination or comprehension failure. Excluding these table cases would reduce Gemini's rate to 2.9\% (12/421).

Once table-attribution collapse is set aside, the genuine content-level failure rate --- cases where a model cites a source for a product that truly does not appear anywhere on that page --- drops to 2.9\% for Gemini (12/421) and 0.7\% for GPT (5/689). In other words, across 1{,}110 solo-cited product claims, only 17 represent cases where the model pointed a reader to a source that could not substantiate the recommendation.

For context, \textcite{wu2025sourcecheckup} evaluated seven LLMs on medical citation accuracy using a substantially more rigorous verification framework (800~questions, 58K~statement--source pairs, physician validation) and found that retrieval-augmented models (GPT-4o and Gemini Ultra with web search) substantially outperform API-only models on both URL validity and statement-level support --- yet even their best-performing configuration (GPT-4o with RAG) achieved only $\sim$70\% statement-level support. Our analysis is narrower in scope --- limited to solo-cited listicle product claims with an LLM judge and manual review rather than a comprehensive statement-level verification pipeline --- and operates in a different domain (commercial products vs.\ medical queries) on newer model generations. Direct comparison of absolute rates is therefore not meaningful, but the directional finding is consistent: grounding infrastructure materially reduces citation errors compared to parametric-only generation, reinforcing the broader argument that retrieval-augmented architectures remain essential for trustworthy AI-mediated search.

This finding reframes the ``hallucination problem'' in production RAG systems. For product recommendations backed by solo-cited listicles, models rarely fabricate facts about a product they have read --- the comprehension layer is robust. The remaining errors are attribution errors: the model ``knows'' the facts but ``forgets'' which specific source it found them in.
